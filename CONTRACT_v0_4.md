# Контракт взаємодії штабу EasyWAR — версія 0.4

Статус: чернетка 0.4. Рішення командира (JE) від 2026-10-15 щодо пропозицій розділу 21 і прогалин звірки застосовано. Очікує затвердження.
Поправки JE від 2026-10-22 (T-0006: A-T5-01…07, A-T5-09; A-T5-08 відкладено) внесено в розділи 1, 2, 9а і 25.1. Інші положення не змінювались.
Замінює v0.3. Військові терміни вжито в загальному значенні, без прив'язки до конкретного статуту.

Позначки в тексті:
- **[ПРИЙНЯТО ЗА ЗАМОВЧУВАННЯМ]** означає рішення, яке я запропонував, а командир ще не підтвердив. Командир може змінити будь-яке.

Зміни відносно v0.3 (за рішеннями JE від 2026-10-15, журнал у розділі 25):
- J4 перейменовано на **ADM** (адмін-відділ). Це лише скрипт, без виконавців з AI. Позначення замінено в усьому тексті, включно з розділами сторони J5.
- Бюджет єдиний; `max_attempts: 2` означає першу спробу плюс одну повторну; третя спроба лише для важливої події і лише за рішенням JE (розділи 2, 3, 4, 13).
- Власна робота начальників і дочірні задачі мають картку, яку створює ADM автоматично (розділи 3, 4, 7).
- Версії й приймання залежать від типу результату: `commit`, `file_hash`, `doc_version`; наказ визначає перевірки (розділи 3, 5, 6, 8).
- Мітки перевірених записів за ролями («перевірено J3», «перевірено J5»); перевірені записи не переписуються, виправлення через `supersedes` (розділи 2, 8).
- ADM перевіряє фактичні модель і інструменти перед призначенням; розділ 10 — план класів, а не каталог (розділи 7, 10).
- C5.2 називається **Gemini-консультант** і самостійності не має (розділи 1, 2).
- Додано позначення C5.3 (Дослідник) і C5.4 (Рецензент логіки), разові (розділ 1).
- Зауваження рецензії самодостатні: опис, місце, посилання на правило, спосіб перевірки (розділи 5, 12).
- Приклад T-0001 (розділ 22) оновлено під ці зміни.

## ЧАСТИНА I. Спільна (не змінюється одностороннім чином)

### 0. Засади

1. **Командування через задум.** Командир ставить мету, кінцевий стан і межі. Спосіб обирає виконавець.
2. **Єдиноначальність.** Кожне завдання має одного виконавця й одного начальника.
3. **Відповідальність не делегується.** Начальник відповідає за результат підлеглих. «Так доповів підлеглий» не є підставою для запису «перевірено».
4. **Доповідь за відхиленням.** Виконавець доповідає на рубежах і при відхиленні від задуму.
5. **Єдине джерело обстановки.** Стан веде лише ADM. Агенти надсилають йому донесення, файли стану не редагують.
6. **Дані.** Усі дані в штабі синтетичні. Правило однакове для всіх зовнішніх виконавців, включно з Claude.
7. **Підтверджене має джерело.** Підтвердження без посилання на файл, коміт чи лог вважається твердженням.
8. **Перевірка прив'язана до версії.** Рецензія й перевірки стосуються конкретного коміту. Нові зміни означають нові перевірки.
9. **Одна сторона пише у файл.** Над одним файлом одночасно працює один виконавець. Пропозиції від іншого відділу йдуть окремою гілкою.

### 1. Склад штабу й підпорядкування

Позначка **Jn** — начальник або напрям. **Cn** — виконавець у напрямі Jn. Якщо виконавців кілька, пишемо Cn.1, Cn.2. **ADM** — адмін-відділ, поза нумерацією.

**[ПРИЙНЯТО ЗА ЗАМОВЧУВАННЯМ]**
- J1 і J2 лишаються назвами напрямів, окремих начальників для них немає. C1 і C2 підпорядковані найближчому начальнику (J5 і J3). Утримувати посади без роботи не будемо.
- Gemini (C5.2) отримує наказ лише від J5. Технічну частину брифа (формат, розмір, сітка, палітра, прозорість, спосіб інтеграції) складає J3 до видачі наказу. J3 командувати C5.2 не може, а лише приймає технічну частину результату.
- У C5.2 немає підлеглих і немає самостійності (рішення JE): він діє лише за параметрами брифа, усе незазначене уточнює у J5. Працює по одній задачі, не змінює напрям і не делегує. Може давати консультації на запит J5 у сфері креативів, візуалізації й відео; такі консультації не мають сили рішення.
- C5.3 і C5.4 разові: J5 запускає їх за потреби, вони рахуються в ліміт двох виконавців відділу, постійної посади не мають і власних підлеглих не створюють. C5.4 не замінює C3.
- C3 підпорядкований J3 організаційно, але висновок рецензії ніхто не редагує. Нове рішення можливе лише повторною рецензією.
- Для ризикових змін (міграції схеми, capabilities Tauri, CSP, legacy HTML, робота з секретами) висновок C3 копіюється командиру. На запит J5 або командира додається міжвендорна рецензія від C5.1. Вона не замінює C3.
- Горизонтальна взаємодія J5↔J3 є **запитом**. Він стає завданням лише після прийняття. Розбіжність вирішує командир.
- Глибина делегування: 1. Виконавці не створюють підлеглих.

### 3. Бойовий наказ (шаблон завдання)

Наказ видає начальник виконавцю. Для власної роботи начальника наказ не потрібен.

```yaml
id: T-0000
version: 1                     # зростає лише з погодженою поправкою
parent_task_id: null           # для дочірніх задач і власної роботи начальників
title: ""

intent:                        # ЗАДУМ
  purpose: ""
  end_state: [""]              # перевіряні умови
  red_lines: ["тільки синтетичні дані"]

mission: ""                    # ЗАВДАННЯ
scope: {in: [], out: []}
context_refs: []
materials: []

data_class: synthetic          # ADM відхиляє будь-що інше
requester: J5
assignee: J3                   # один виконавець
priority: normal               # змінює лише JE
important: false               # ознака важливої події (ставить requester, змінює JE); дає право просити третю спробу

acceptance:
  technical: J3
  content: J5
  key_decision: false          # true: остаточно приймає JE

checks:                        # ПЕРЕВІРКИ визначає наказ; якщо блоку немає, діють правила для коду
  subject_kind: commit         # commit | file_hash | doc_version
  verify: []                   # команди або перевірки, які мають пройти
  review_kind: code            # code (C3) | logic (C5.4) | none

resources:                     # обмеження, а не оцінки
  max_calls: 40
  max_tokens: null             # null, якщо провайдер не дає обліку
  max_cost_usd: null
  max_attempts: 2              # усього спроб на крок: перша плюс одна повторна; третя лише за рішенням JE
  max_delegation_depth: 1
  reviewer: {max_read_files: 15}
  reserve_pct: 0
  accuracy: estimate
  effort_estimate: {value: "~30 хв", accuracy: estimate}   # лише інформація

reporting:
  milestones: []
  thresholds:
    resources_used_pct: 70
    on_last_attempt: true
    on_provider_limit: true
    on_review_incomplete: true
    on_red_line_risk: true

amendments: []
```

Правила:
- Наказ діє після `task_accepted`. Після прийняття поля незмінні. Зміни лише через поправки.
- Коли ресурси вичерпано, виконавець зупиняється й подає донесення про відхилення. Стан: `blocked`, причина `awaiting_founder`.
- Якщо `max_tokens` або `max_cost_usd` дорівнює `null`, діють `max_calls` і `max_attempts`.
- **Єдиний бюджет.** Витрати підлеглих, перевірок і повторів входять у бюджет батьківської задачі. ADM резервує ресурс перед запуском, невикористаний залишок повертається. Зміна виконавця не обнуляє витрат і використаних спроб.
- **Одиниця `max_calls`** визначається для кожного маршруту окремо (запит до моделі чи виклик інструмента). ADM резервує лише те, що здатен облічити; решта має `estimate` або `unknown`.
- **Важлива подія** (право просити третю спробу): `important: true`, ризикова зміна (міграція схеми, capabilities Tauri, CSP, legacy HTML, секрети) або блокер для наступних задач. Третя спроба потребує рішення JE.
- **Картка.** Наказ самому собі не потрібен, але кожна робота, включно з власною роботою начальників і дочірніми задачами, має картку з `id`, `parent_task_id`, виконавцем, requester, станом і часткою бюджету. Картку створює ADM автоматично при `task_accepted`, вручну її не ведуть.

### 4. Журнал дій і поправки

Журнал (`events.jsonl`) лише додається.

| Подія | Хто створює | Чинність |
|---|---|---|
| `task_created` | requester | одразу |
| `task_accepted` | assignee | одразу |
| `amendment_proposed` | requester або assignee | не діє до погодження |
| `amendment_approved` / `rejected` | за таблицею нижче | створює нову `version` |
| `reassignment_proposed` | requester, assignee, ADM (при ліміті) | не діє до погодження |
| `reassignment_approved` | requester; при зміні обсягу ще JE | нова версія, донесення зберігаються |
| `delegation_started` / `finished` | assignee | одразу |
| `report_filed` | автор донесення | одразу |
| `review_requested` / `finished` | assignee / C3 | прив'язано до `subject` |
| `acceptance` | роль із `acceptance` | прив'язано до `subject` |
| `command` | людина через адаптер офісу | ADM перевіряє право |
| `card_created` | ADM (автоматично) | при `task_accepted` |
| `third_attempt_approved` | JE (через `command`) | лише для важливої події |

Для `review_finished` і `acceptance` поля `review_status`, `result` і `scope` обов'язкові для зарахування бар'єром приймання (розділ 6): бар'єр читає лише явні `review_status: complete`, `result: accepted`, `scope: full`; інші значення або відсутність поля бар'єр не відкривають; `scope: limited` з `limits: [...]` зберігає часткове приймання в історії; `scope: full` із непорожнім `limits` — суперечливий запис, не зараховується (T-0012, рішення JE 2026-10-28).

Нові події `report_filed` і `escalation`, які ADM/J4 Bridge додає з посиланням `ref` на журнал J4, містять `ledger_hash` запису журналу і `installation_id` установки J4 (T-0011); `j4 close` їх звіряє, історичні події не переписуються (розділ 9а, п. 3).

| Що змінюється | Погоджує |
|---|---|
| Бюджет понад `reserve_pct` | JE |
| Обсяг або кінцевий стан | JE |
| Пріоритет | JE |
| Уточнення без зміни обсягу | requester |
| Використання резерву | виконавець, з доповіддю |
| Перепризначення без зміни обсягу | requester |
| Третя спроба на кроці (важлива подія) | JE |

```yaml
- id: A-1
  proposed_by: J3
  base_version: 1
  change: {field: resources.reviewer.max_read_files, from: 15, to: 25}
  reason: ""
  status: proposed             # proposed | approved | rejected
  decided_by: null
  decided_at: null
```

### 5. Донесення (шаблон контрольної точки)

Донесення лише додаються. Чужі не редагуються.

```yaml

task_version: 1
seq: 1
author: J3                     # J3 | C2 | C3 | C5.1 | ADM | ...
kind: milestone                # milestone | deviation | before_handoff | before_costly_op | auto_on_limit
at: 2026-10-15T14:20:00+03:00
subject: {kind: commit, ref: a1b2c3d}   # kind: commit | file_hash | doc_version

situation:                     # ОБСТАНОВКА
  current_step: ""
  tool_results_refs: []
  done: []
verified:                      # ПІДТВЕРДЖЕНО, лише з джерелом
  - claim: ""
    evidence: {kind: log, ref: ""}     # file | commit | log
    subject_ref: a1b2c3d
claimed: []                    # НЕ ПІДТВЕРДЖЕНО
deviation:                     # ВІДХИЛЕННЯ; null, якщо немає
  type: null                   # resources | provider_limit | review_incomplete | red_line_risk | new_circumstance
  detail: ""
review:
  review_status: null          # complete | incomplete | null
  verdict: null                # passed | changes_requested | null
  subject_ref: null
  unread: []
  files_read: []
findings:
  - id: F-1
    severity: high             # high | medium | low
    mandatory: true
    status: open               # open | closed | deferred
    description: ""            # у чому дефект
    location: ""               # або evidence_ref: де саме (файл:рядок, лог, кадр, джерело)
    criterion_or_rule_ref: ""  # на яке правило, вимогу чи критерій посилається
    how_to_verify: ""          # як перевірити виправлення
    closed_by: null            # {subject_ref, re_review_ref}, коли closed
decision_needed: []            # РІШЕННЯ рівня C
remaining: []
next_action: ""
```

Коли подається донесення:
- на кожному рубежі та після завершеного етапу;
- перед передачею іншому виконавцю й перед дорогою операцією;
- при досягненні порогу з `reporting.thresholds` (тип `deviation`);
- автоматично (`auto_on_limit`), коли вичерпано ліміт провайдера: ADM зберігає поточний крок і результати інструментів, навіть якщо агент не встиг скласти донесення.

Правила:
- `verified` без `evidence` і `subject_ref` недійсне, ADM його відхиляє.
- `verified` діє лише для свого `subject_ref`.
- `review_status: incomplete` не є успішною перевіркою, `verdict` тоді `null`.
- `review_status: complete` не означає схвалення. Схвалення дорівнює `verdict: passed`.
- Вичерпання `max_read_files` дає `incomplete` з переліком `unread`.
- Обов'язкове зауваження закриває лише рецензент після повторної рецензії актуальної версії результату (C3 для коду, C5.4 для логіки).
- Зауваження самодостатнє: `description`, `location` або `evidence_ref`, `criterion_or_rule_ref`, `how_to_verify`. Закриття містить актуальний `subject_ref` і посилання на повторну рецензію.
- Для некодових результатів `subject` — це `file_hash` або `doc_version`, незмінні ідентифікатори версії.

### 6. Карта обстановки (шаблон стану)

Файл веде лише ADM. Стан і причина очікування записуються окремо.

```yaml
task_id: T-0000
task_version: 1
assignee: J3
model: {name: "", accuracy: exact}         # exact | estimate
state: queued                  # queued | working | waiting | review | blocked | done | failed
wait_reason: null              # provider_limit | rate_limit | awaiting_founder | awaiting_agent |
                               # review_incomplete | changes_requested | dependency | null
wait_detail: null
resume_at: {value: null, accuracy: unknown}      # exact | estimate | unknown
progress: {done: 0, total: 0, accuracy: estimate}
usage:
  calls: {value: 0, accuracy: exact}
  tokens: {value: null, accuracy: unknown}
  cost_usd: {value: null, accuracy: unknown}
budget_left: {calls: 40}
last_report: null
current_subject: null
updated_at: ""
```

Правила переходів:
- `review_status: incomplete` дає `state: review`, `wait_reason: review_incomplete`.
- `verdict: changes_requested` дає `state: working`, `wait_reason: changes_requested`, поки є відкриті обов'язкові зауваження.
- Ліміт провайдера дає `state: waiting`, `wait_reason: provider_limit`. Завдання чекає відновлення або проходить погоджене перепризначення.

Карта обстановки (піксельний офіс):
- читає стан через адаптер до ADM, у файли стану напряму не пише;
- `state` визначає поведінку персонажа, `wait_reason` визначає підпис причини;
- дії користувача (пауза, відновлення, погодження поправки, зміна пріоритету) надсилаються ADM як `command`, а ADM перевіряє право за розділом 2.

**Умови переходу в `done`.** ADM дозволяє `done`, лише коли виконано все, що вимагає наказ (`checks`), і:
1. Перевірки з `checks.verify` пройдені на актуальному `current_subject` (для коду це команди розділу 13).
2. Остання завершена рецензія виду `checks.review_kind` на тому ж `subject` має `verdict: passed`. Для `code` це C3, для `logic` це C5.4, для `none` пункт не застосовується.
3. Усі обов'язкові зауваження закриті із джерелом.
4. Є `acceptance` від кожної ролі з поля `acceptance` на тому ж `subject`. Приймання зараховується лише повне: `result: accepted`, `scope: full` (T-0012, рішення JE 2026-10-28).
5. Для `key_decision: true` є приймання JE.

Правила за замовчуванням: якщо наказ не містить `checks`, діють правила для коду. Будь-яка зміна файлів репозиторію (документація, конфігурація, legacy HTML, міграції) завжди проходить C3, а ризикові зміни додатково копіюються JE. Результат дослідження, на якому тримається технічне чи безпекове рішення, J3 перевіряє вибірково (2–3 джерела).

### 7. Облік

- Кожне число має `accuracy`: `exact` (дані провайдера чи лог), `estimate` або `unknown`.
- Залишок і час відновлення показуються лише коли їх дає провайдер.
- Облік веде ADM за провайдером, моделлю, посадою й завданням. Субскрипційні ліміти, обмеження частоти запитів і витрати API окремі.
- Облік охоплює й власну роботу начальників (картки, розділ 3).
- Перед призначенням ADM перевіряє фактичний runtime, provider, `model_id` і підтримувані інструменти. Назви моделей у розділах 10 і 16 — план класів, а не підтверджений каталог. `unknown` дозволене для моделі й часу відновлення, оцінені часи показуються лише з позначкою `estimate`.

### 8. Прийом результатів

| Що | Приймає |
|---|---|
| Реалізація, технічні перевірки | J3 |
| Зміст, відповідність брифу, зовнішні джерела | J5 |
| Ключове візуальне рішення | JE |
| Технічна частина матеріалів C5.2 (формат, розмір, сітка, прозорість) | J3 |
| Зміст матеріалів C5.2 | J5 |
| Код від C5.1 | J3 (через власну інтеграцію й перевірки) |
| Результат дослідження, що обґрунтовує технічне чи безпекове рішення | зміст приймає J5, джерела вибірково (2–3) перевіряє J3 |

Ключове візуальне рішення: зміна стилю чи палітри офісу, дизайн персонажів, нова візуальна мова інтерфейсу. Позначає requester, JE може змінити.

Записи у спільній пам'яті:
- «перевірено J3» (реалізація, архітектурні рішення, результати перевірок) пише лише J3 після огляду джерела. Старий запис «перевірено Claude» вважається синонімом, доки його не замінено.
- «перевірено J5» (зовнішні джерела, зміст, відповідність брифу) пише лише J5, з доказом і версією. Технічних тверджень J5 не підтверджує.
- «оформлено Діловодством» (пакети, зведення) пише C1. Перевірені записи C1 не переписує, розбіжності передає тому, хто перевірив.
- Перевірені записи не змінюються й не видаляються. Виправлення створює новий запис із `supersedes` і `reason`, старий лишається в історії, C1 зберігає обидва.
- Неперевірені технічні твердження в пакеті мають позначку «не підтверджено», і виконавці не спираються на них як на факт.

### 9. Захист даних

1. Реальні дані лежать поза штабом і поза репозиторієм.
2. Кожен агент запускається з переліком дозволених каталогів у конфігурації інструмента, а не лише в тексті інструкції. Каталог із реальними даними не входить до жодного переліку, включно з J3.
3. ADM відхиляє наказ із `data_class`, відмінним від `synthetic`.
4. Сканер секретів і схожих на реальні шаблонів є страховкою перед відправленням і комітом. Він не замінює пунктів 1–3.
5. Для кожного інструмента перевіряємо практично, що він не читає каталог поза переліком.

### 9а. ADM і J4 Bridge (рішення JE від 2026-10-22, T-0006)

1. **Роль і компонент (A-T5-01).** ADM — офіційна роль координатора штабу. J4 Bridge — програмний компонент ADM. Канонічна реалізація — `bridge/` (Node.js); друга незалежна реалізація не допускається.
2. **Runtime J5 (A-T5-02).** J5: runtime — OpenAI Responses API через J4; правила ролі — `bridge/roles/J5.md` (версія й sha256 у журналі J4); модель задає погодження JE, ідентифікатор фіксується з відповіді провайдера. J5 через J4 не має інструментів і доступу до репозиторію. Вибір інтерфейсу не є дозволом на платні виклики. Codex (C5.1) роль J5 не виконує.
3. **Журнал (A-T5-04).** Журнал J4 (`ledger.jsonl` з ланцюгом хешів) — технічний доказ доставки, обліку викликів і рішень маршрутизатора. `events.jsonl` задачі лишається єдиним журналом дій. Після появи ADM: J4 додає в `events.jsonl` `report_filed` / `escalation` з посиланням `ref` на запис журналу J4 (файл і `seq`). Нова подія містить також `ledger_hash` цього запису і `installation_id` установки J4; «нова» — з посиланням на запис журналу, пізніший за запис прив'язки журналу до установки (`installation` або `installation_adopted`), а для запису до прив'язки обов'язковий лише `ledger_hash` (T-0011).
4. **Облік (A-T5-05).** Для маршрутів J4 одиниця `max_calls` — один виклик адаптера. `calls` — `exact`; токени — `exact`, якщо провайдер повернув `usage`, інакше `estimate` (резерв); вартість — `estimate` за ціною з погодження JE або `unknown`. Виклик із невідомим результатом після збою зараховується як витрачений (`estimate`). Одиниці (виклик, токен, мікродолар USD) і точність кожного числа вказуються явно.
5. **Місячна стеля (рішення JE).** Сукупна верхня межа платних викликів через ADM/J4 Bridge — $50 USD на календарний місяць UTC, не окремо для кожного агента. Пороги: $35 — попередження, $45 — критичне попередження, $50 — блокування нових платних викликів. Облік зберігається між перезапусками й не скидається при зміні задачі; підтверджені витрати й оцінка ведуться окремо; невизначений результат зараховується консервативно (весь резерв); перед викликом резервується верхня межа вартості, інакше виклик відхиляється. Stub-виклики не зараховуються. Навіть за залишку бюджету платний виклик без окремого погодження JE заборонений. Змінює стелю лише JE.
6. **Захист даних (A-T5-06).** Агент через J4 отримує лише конверт і тіло повідомлення; файли репозиторію J5 не надсилаються. J4 відхиляє повідомлення з `data_class`, відмінним від `synthetic`, і блокує повідомлення та відповіді, де спрацював сканер (секрети, координати, MGRS, телефони). У журнал J4 не потрапляють тексти тіл, зібрані промпти, сирі відповіді й ключі — лише хеші; рівень доказів `summary` або `hash` визначає JE.
7. **Незалежна рецензія C5.1-R (A-T5-07, умовно).** Міжвендорна рецензія C5.1 виконується окремим запуском Codex у режимі read-only під позначенням C5.1-R; J4 перевіряє, що `run_id` рецензії не збігається із запуском автора, а рецензент не є автором. C5.1-R не замінює C3 без окремого дозволу JE.
8. **Завершення задачі.** Стан `done` встановлює лише ADM після бар'єра приймання (розділ 6, умови переходу в `done`), усі приймання — на одному `subject`. Повідомлення агентів стан `done` встановити не можуть.
9. **Відкладено (A-T5-08).** Передача задач J5 → C5.1 через J4 — після окремої перевірки маршруту й рішення JE. До того J4 не передає задач від J5 до C5.1 автоматично.

## ЧАСТИНА II. Сторона J3 (заповнено)

### 10. Склад і моделі відділу J3

Доступні мені класи моделей: Haiku 5.5, Sonnet 5.5, Opus 5.5, Fable 5.1. Цінових і лімітних даних у цьому сеансі немає, тому «дешевша» й «сильніша» означають клас моделі. Облік числами додає ADM. Таблиця нижче — план класів моделей, а не підтверджений каталог: фактичний `model_id` за маршрутом підтверджує ADM (розділ 7).

| Позн. | Посада | Модель за замовчуванням | Коли підвищується |
|---|---|---|---|
| J3 | Начальник поточних операцій | Sonnet 5.5 | Opus 5.5: складна архітектура, міграції, legacy-код |
| C2 | Розвідка | Haiku 5.5 | Sonnet 5.5, якщо звіт мав хибні пункти |
| C3 | Контроль виконання | Sonnet 5.5 | Opus 5.5: міграції, capabilities, CSP, legacy HTML |
| Тестописець (разова роль) | Однотипні юніт-тести за специфікацією | Sonnet 5.5 | — |

Fable 5.1 у постійному складі немає. Це найсильніша з доступних, її лишаю для рідкісних випадків, коли Opus не впорався або ризик найвищий.

Статус підтвердження сторони J3 (на 2026-10-15):

```yaml
J3_confirmation:
  model_ids: unknown                 # у сеансі відомий лише налаштований ідентифікатор; фактичний підтверджує ADM
  allowlist_tests_completed: false   # розділ 9, п. 5 не виконано для маршруту J3
  current_session_directory_limits: "не налаштовані за контрактом"
```

### 11. Що виконує J3

| Посада | Що робить | Що повертає |
|---|---|---|
| J3 | реалізація, технічні перевірки, інтеграція пропозицій C5.1, технічна частина брифа для C5.2, приймання технічного | код у основній гілці, донесення, записи «перевірено J3» |
| C2 | шукає по репозиторію: де реалізовано, що торкається міграції, чи є дублі в `air.html` і `rocket.html`, які тести покривають модуль | список `файл:рядок` з одним реченням, без вставок коду |
| C3 | рецензує зміни: правила репозиторію, правка в обох legacy-файлах, секрети, вимкнені тести, відповідність документації | висновок `passed` або `changes_requested`, зауваження зі ступенем серйозності й посиланням на правило, перелік відкритого |

Тестописця запускаю, лише коли тестів багато й вони однотипні.

Те, що J3 не делегує: архітектура, міграції, Rust-ядро, правки legacy HTML, усе про capabilities, CSP, секрети й дані, приймання результатів, запис рішень.

### 12. Правила для C2 і C3

**C2 (Розвідка).** Лише читання. Повертає список `файл:рядок`. J3 відкриває 2–3 пункти вибірково. Один хибний пункт означає повну перевірку звіту.

**C3 (Контроль виконання).**
- Починає з diff, формулювання завдання й `AGENTS.md`, без міркувань автора.
- Далі читає сусідній код, схему БД, міграції й тести. Права лише на читання.
- Звіт вказує, що саме відкривав. Зауваження без такого посилання не приймаються.
- Кожне зауваження самодостатнє: опис, місце або посилання на докази, посилання на правило чи критерій, спосіб перевірки (розділ 5).
- Вичерпав `max_read_files`: повертає `review_status: incomplete` і перелік `unread`.
- Кожне зауваження J3 перевіряє сам, перш ніж діяти. Відсутність зауважень не дорівнює схваленню.
- Для ризикових змін висновок копіюється командиру. На запит J5 або JE додається міжвендорна рецензія C5.1.

### 13. Перевірка роботи

- «Тести пройшли» приймається лише з виводу команди перевірки: `npm run test:unit`, `cargo test`, `cargo clippy -D warnings`, `cargo fmt --check`, `npm run build`, `node script/release_version.mjs`. Не зі слів виконавця. Запуск виконує скрипт, не AI.
- Дві спроби на крок: перша плюс одна повторна. Після цього J3 виконує задачу сам. Третя спроба можлива лише для важливої події і лише за рішенням JE (розділи 2, 3).
- Правки `air.html` і `rocket.html` не делегую.

### 14. Паралельність відділу J3

- Не більше двох виконавців одночасно.
- C2 може працювати паралельно (лише читання).
- Два виконавці, що пишуть, не працюють над одними файлами.
- Глибина делегування 1.

### 15. Що J3 очікує від J5

- Завдання у форматі наказу (розділ 3) з заповненими `intent`, `end_state`, `red_lines`, `acceptance`.
- Для C5.2 пакет із двома частинами: задум і композиція від J5, технічні обмеження від J3.
- Позначку «клас даних: synthetic» у кожному пакеті.
- Код від C5.1 у окремій гілці як пропозицію, з описом, що змінено й чому.

## ЧАСТИНА III. Сторона J5 (заповнено ChatGPT)

> Нотатка ChatGPT: заповнений фрагмент для вставлення замість розділів 16–21; очікує затвердження JE. Частини I, II, IV і V вихідного контракту не змінені. Пропозиції розділу 21 не набувають чинності автоматично.

Усі шість YAML-блоків розібрано парсером без помилок. Статуси пропозицій розділу 21 оновлено за рішенням JE від 2026-10-15 (розділ 25). #### Разові режими без постійних посад

**Дослідник.**  Працює з зовнішніми джерелами: офіційна документація, приклади, альтернативи, обмеження. Повертає перелік джерел, дату доступу, стислий витяг, відокремлені факти й припущення. J5 відкриває джерела, на яких ґрунтується рішення, перевіряє актуальність і підтримку висновків. Пошук по репозиторію залишається C2.

**Рецензент логіки.**  Починає зі специфікації, кінцевого стану й обмежень, без міркувань автора. Перевіряє суперечності, пропущені сценарії, неоднозначні критерії та зайві дії користувача. Повертає конкретні зауваження з посиланнями на вимоги й прикладами. J5 перевіряє кожне суттєве зауваження; зміни архітектурної частини узгоджує з J3. Режим не замінює C3.

Обидва режими запускає J5 як виконавців першого рівня під окремими ідентифікаторами запуску ADM. Вони не є підлеглими C1 чи C5.1 і не створюють власних підлеглих. Їхні модель, облік і призначення запусків мають бути налаштовані відповідно до правил розділу 19.

У поточному сеансі доступ до файлової системи не обмежений allowlist каталогів штабу. Тому відповідність пунктам 9.2 і 9.5 не підтверджена. Синтетичний клас цієї документації не означає, що технічне обмеження доступу вже встановлене.

До запуску працівників у цільовому workspace для кожного маршруту перевіряємо дозволене читання, заборонене читання поза переліком, запис за межами дозволеного та обхід через посилання. Результати оформлюються джерелами перевірки. Gemini отримує лише відібраний пакет через адаптер; доступ до репозиторію для його творчої задачі не надається без потреби.

Матеріали J5: специфікація з версією, критерії, контекст, посилання на зображення або візуалізацію. J3 не має відновлювати задум із неповної історії чату. Ключове непогоджене рішення передається JE, решта уточнень вирішується між J5 і J3 в межах повноважень.

## ЧАСТИНА V. Відкрите і журнал рішень

### 23. Для рішення командира (залишилося відкритим)

1. Підтвердити позначки **[ПРИЙНЯТО ЗА ЗАМОВЧУВАННЯМ]** з розділу 1.
2. Пороги доповіді: 70 % ресурсів і «остання спроба» є початковими, уточнюємо після перших завдань.
3. `reserve_pct`: дорівнює 0, тобто будь-яке збільшення бюджету погоджує командир.
4. Форма наказу й донесення: якщо в практиці командира є усталений порядок пунктів, замінюємо ним мою схему.
5. **Критерій «важливої події»** для третьої спроби (розділ 3). Я запропонував: `important: true` від requester, ризикова зміна (міграція схеми, capabilities Tauri, CSP, legacy HTML, секрети) або блокер для наступних задач. Підтвердити чи змінити.
6. **Роль Gemini-консультанта.** Назву й відсутність самостійності ви задали. Я залишив обсяг роботи (креативи, візуалізація, відео за брифом) і дозволив консультації на запит J5 у цій сфері без сили рішення. Якщо «консультант» означає ширше коло питань, скажіть.

### 24. Для версії 0.5

1. Платформа карти обстановки. Критерій: читає стан через адаптер до ADM, дії передає як `command`, не змінює стан напряму.
2. Облік токенів і вартості залежить від даних провайдера. До перевірки `unknown`.
3. Практична перевірка переліків дозволених каталогів для кожного маршруту, включно з J3 (розділ 9, п. 5).
4. Мінімальний ADM і ручний прохід T-0001 (розділ 26).
