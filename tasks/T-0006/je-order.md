1. Намір командира

У штабі EasyWAR має функціонувати одна узгоджена, контрольована й відновлювана система координації агентів.

ADM — офіційна роль координатора штабу. J4 Bridge — програмний компонент ADM.

Єдиною канонічною реалізацією визначено:

bridge/ — Node.js

Реалізація j4_bridge/ на Python із PR #3 не стає другим робочим мостом.

Мета T-0006 — усунути архітектурне дублювання, привести реалізацію до рішень JE та завершити документальне оформлення контракту.

Не переписувати Bridge з нуля.

3. PR #2 — історичне злиття

JE визнає злиття PR #2 дозволеним винятком.

Це рішення:

* Не скасовує факт злиття.
* Не означає, що C3 уже провів рецензію.
* Не створює заднім числом технічного або змістового приймання.
* Не дозволяє обходити рецензії надалі.

J3 повинен:

1. Зафіксувати рішення JE окремою подією журналу з посиланням на PR #2 та merge SHA 5e1363fa5df9e07279ddedc3695d13bf61592597.
2. Провести ретроспективний аудит безпеки коду Node Bridge.
3. Залучити C3 для незалежної перевірки поточної версії.
4. Зберегти історичні записи без переписування.
5. Новими подіями відобразити результат аудиту та поточний статус.

Виняток JE стосується лише історичного злиття PR #2, а не майбутніх змін.

4. PR #3 — припинення паралельної реалізації

PR #3 не зливати в поточному вигляді.

Із Python-прототипу перенести до Node лише відсутні можливості:

1. Перевірка acceptance_ready: усі обов’язкові приймання прив’язані до одного commit SHA.
2. Відхилення недозволеного завершення задачі зі станом done.
3. Місячний контроль витрат із порогами попередження.

Не переносити:

* Python runtime як другий Bridge.
* Дубльовані протоколи та маршрутизатори.
* Журнал із повними текстами повідомлень.
* SQLite без окремо доведеної потреби.
* Призначення Codex на роль J5.
* Автоматичне схвалення рішень рівня C.

Після інтеграції та перевірки потрібних механізмів закрити PR #3 як замінений T-0006, залишивши посилання на коміт нової реалізації.

Обов’язково:

* Не допускати перевищення ліміту через паралельні запити: перед запуском резервувати верхню межу можливої вартості або відмовляти в запиті.

Важливо: навіть за залишку $50 платний виклик заборонений без окремого погодження JE.

Погодження живого виклику повинно визначати провайдера, модель, кількість запитів, ліміт токенів, максимальну вартість і строк дії.

Зміна місячної стелі — виключно рішення JE.

10. Порядок виконання

Етап 1 — реєстрація. Створити tasks/T-0006/order.yaml, записати рішення JE та подію прийняття задачі. Визначити один базовий SHA.

Етап 2 — документація. Узгодити контракт, AGENTS.md, роль ADM, протокол і бюджетну модель.

Етап 3 — реалізація. Додати до Node Bridge відсутні механізми, не дублюючи вже наявні.

Етап 4 — перевірка. Виконати наявні 49 тестів, нові тести приймань і бюджету, сценарії відновлення та незалежну рецензію C3.

Етап 5 — приймання. J3 виконує технічне приймання, J5 — змістове, обидва на одному commit SHA.

Етап 6 — завершення. Після всіх приймань та штатного злиття закрити PR #3 як замінений, зафіксувати фактичні SHA і завершити T-0006.

11. Критерії успіху

T-0006 вважається виконаним, якщо:

1. Node bridge/ — єдина канонічна реалізація.
2. ADM та J4 Bridge чітко розмежовані.
3. J5 не підміняється Codex.
4. Платні виклики без дозволу JE неможливі.
5. Місячна стеля $50 та пороги $35/$45/$50 працюють.
6. Рішення рівня C неможливо автоматично схвалити.
7. Приймання перевіряються на одному SHA.
8. Журнал не містить секретів і повних текстів повідомлень.
9. Відновлення після збоїв та ідемпотентність підтверджені тестами.
10. Поправки A-T5-01…09 документально врегульовані.
11. C3, J3 та J5 підтвердили один контрольний коміт.
12. PR #3 закритий із поясненням та посиланням на замінну реалізацію.

Живий виклик OpenAI не є критерієм приймання T-0006 і залишається окремим наступним етапом.
