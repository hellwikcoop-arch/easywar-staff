# T-0015 — Відновлення, моніторинг і контроль ресурсів J4

**Статус: ПРОЄКТ НАКАЗУ (чернетка J3 для J5) — не зареєстровано.** Програма JE 2026-10-28 п. 1; підготовка ≠ дозвіл.
**Ініціатор:** J5 · **Виконавець:** J3 · **Координатор:** ADM / J4 · **Режим:** synthetic-only, stub, без планувальника.
**Залежність:** після T-0011 (`ledger.mjs`, `bin/j4.mjs`); паралельно з T-0013 лише за розділення команд CLI в окремі модулі (граф). Поза критичним шляхом.

## 1. Мета

Три прогалини, видимі з T-0009…T-0012: (а) **облік ресурсів ведеться вручну** (`calls-ledger.yaml`; відхилення Р-Т12-10 — 28 незапланованих
викликів, бо прогноз і факт звіряє людина); (б) **стан мосту не видно одною командою** (черга, нитки, відкриті ескалації з трьох джерел,
бюджети задач і місячна стеля, останній `recover`, цілісність журналу) — усе дістається окремими `inbox`/`escalations`/`budget`/`verify`;
(в) **відновлення перевірене для черги** (`recover`, `repairIfNeeded`), але не для обірваного `syncTaskEvents`, застарілих замків і
переповнення спулу. Мета — `j4 status` (лише читання), автоматичний підрахунок викликів із журналу J4 з порогами з наказу
(`reporting.thresholds`), і тести відновлення для кожного кроку з записом.

## 3. Завдання J3 (після воріт)

1. `j4 status [--task T-XXXX] [--json]` (лише читання, `Store.open`, `readLedgerStrict`): черга/нитки/спул, відкриті ескалації з трьох джерел і їх джерело, бюджет задачі (`used/limit/forecast`), місячна стеля, цілісність журналу (`verifyLedger`), ідентичність установки (T-0011), стоп-кран; коди виходу 0 / 3 (джерела нечитні) / 4 (стоп-кран).
2. Облік: `j4 budget --task` рахує `dispatch_attempt` із журналу за `task_id`, звіряє з `max_calls` наказу і з `reporting.thresholds`; `forecast` для повного прогону зберігається в `J4_HOME/budget/<task>.json` (`guards.mjs`), перевищення → відмова dispatch (як нині) + ескалація за G3.
3. Відновлення: тести на обрив (а) між `finalize` і `syncTaskEvents` (подія не записана → при наступному `run --once` — дописується без повторного dispatch), (б) застарілий замок обробника (`staleMs`) з мертвим PID, (в) обірваний останній рядок журналу + повторний запуск (`ledger_repaired` один раз), (г) спул без журналу → `dispatch_outcome_unknown`, спроба зарахована; кожен — з мутантом.
4. `j4-tick.sh`: вихідний код і рядок `tick.log` з підсумком `status --json` (без вмісту повідомлень); планувальник не вмикається.
5. DESIGN §21 (моніторинг і відновлення), README (`status`, `budget`), `reports/T-0015/`.

**Не входить:** `acceptance.mjs`, `close.mjs`, `router.mjs`/`events.mjs` (T-0013), `store.mjs` (крім читання), `bridge/config/**`, `.github/**`, live, планувальник, зміна лімітів задач, EasyWAR.

## 4. Критерії приймання

(1) `status` не створює і не змінює файлів (`tree` до/після, як T-0010 B2), 0 dispatch; (2) лічильник із журналу збігається з ручним `calls-ledger`
на T-0012 (76 ⇔ 44 + 4 + 28: прямі — константа за G2) і на синтетичних журналах; (3) поріг 70 % дає видимий сигнал до перевищення; перевищення
`max_calls` → жодного нового dispatch; (4) кожен сценарій відновлення завершується без повторного виклику адаптера і без дубльованих подій
(`j4_key`); (5) журнал із порушеним ланцюгом → `status` код 3 з причиною, не «ок»; (6) C3 за diff; технічне J3, змістове J5; `key_decision: false`
(модель довіри не змінюється), якщо G5 = «ні».

## 5. Ліміти й облік (прогноз, не рішення)

Цільові тести відновлення — ~20 dispatch (stub); повний прогін ×1 ≈ 100 після T-0013 (або ~60, якщо T-0015 іде до T-0013) → **120** без CI;
CI — лише за дозволом, +100. Облік — як у T-0012, але з п. 2 — лічильник автоматично звіряється з ручним.

## 6. Ризики

R15-1 `status` читає три джерела — нечитне джерело має давати код 3, не частковий «ок»; R15-2 автоматичний лічильник не бачить прямих
`adapter.call()` (G2); R15-3 спільний `bin/j4.mjs` з T-0013; R15-4 `health_report` як подія ADM розширює §4 контракту (G5 — пропозиція «ні»).
