1. Рішення командира

Затверджую наказ T-0002 v1 з наведеними нижче уточненнями.

Дозволяю J3 виконати всі чотири підетапи C1a–C1d відповідно до order.yaml, brief.md, CONTRACT_v0_4.md та архітектурних документів EasyWAR, прийнятих через PR #155.

J3 призначений головним виконавцем. J5 здійснює незалежний архітектурний контроль і змістове приймання.

2. Затверджені рішення JE

* JE-01: дозволено реалізацію C1a–C1d у межах T-0002.
* JE-T1: наказ T-0002 v1 прийнято; important: true підтверджено.
* JE-02: включити машину станів вступу за коротким кодом Pair до C1c.
* JE-T2: схвалення вступу може виконувати учасник, який має всі необхідні епохи ключів, за умови взаємної згоди сторін та дотримання чинних правил колективу.
* JE-T3: класифікацію полів визначати за смисловою роллю, а не лише технічним типом. Невідомий або непідтверджений клас — D. Автоматично запропонований клас не вважається підтвердженим.
* JE-T4: CONTRACT_v0_4.md застосовується до T-0002 як чинний робочий контракт. Накази, донесення та події вести в репозиторії easywar-staff, гілка setup/staff-bootstrap.
* JE-T5: J3 може самостійно зливати PR після технічного приймання J3, незалежної рецензії C3 та змістового приймання J5, усі на відповідному коміті. Без приймання J5 злиття заборонено.

3. Обсяг виконання

C1a — Чутливість і маршрутизація

Створити чисте JS-ядро визначення класу чутливості. Клас таблиці дорівнює найвищому класу її полів. Невідомий клас — D. Клас D дозволено лише через LAN. WAN Mesh залишається забороненим для всіх класів.

C1b — Операції спільних таблиць

Реалізувати чисту логіку операцій над рядками, виявлення конфліктів, перевірку op_id, видалення та відновлення. Заборонено приховане перезаписування за принципом last-write-wins.

C1c — Членство та Pair

Реалізувати чисту логіку членства, вступу, відкликання, виходу, стану PENDING_HISTORY та машину станів вступу за кодом.

Реальна генерація кодів, криптографічний обмін, PAKE, SAS і мережевий пошук учасників до C1 не входять.

C1d — Політики обміну та «Доповісти»

Реалізувати логіку політик комбінованої синхронізації та попереднього перегляду передачі.

Автоматична відправка, ручне приймання та вимкнення синхронізації залишаються неактивними до окремих рішень JE. Відхилення має повертати причину OwnerDecisionRequired.

4. Червоні лінії

У межах T-0002 заборонено:

* Змінювати Rust, SQLite-міграції, Tauri capabilities, CSP, Cargo.*, AGENTS.md та legacy HTML.
* Додавати мережеві інтеграції, залежності або підключати нові JS-модулі до робочого застосунку.
* Реалізовувати криптографію, обмін реальними даними або фонову синхронізацію.
* Використовувати реальні операційні дані в тестах.
* Активувати функції, для яких потрібні окремі рішення JE.

Усі нові ядра повинні залишатися ізольованими, детермінованими й перевірятися синтетичними тестами.

5. Порядок виконання та приймання

Виконувати C1a → C1b → C1c → C1d окремими PR. Допускається підготовка C1c паралельно з C1b лише без порушення правила одного автора на файл.

Для кожного підетапу:

1. Реалізація у власній гілці.
2. Локальні тести та npm run test:unit.
3. Відкриття PR і перевірка CI.
4. Незалежна рецензія C3 на конкретному коміті.
5. Технічне приймання J3.
6. Змістове приймання J5 на тому самому коміті.
7. Злиття J3 лише після всіх приймань.

Зміна коміту після рецензії або приймання вимагає повторної перевірки відповідних змін.
