### C1b — операції над рядками спільної таблиці

**Файли:** `src/shared-table-core.js`, `tests/shared-table.test.mjs`.
**Залежності:** C1a не потрібен.

| Експорт | Зміст |
|---|---|
| `OPERATION_KINDS` | `['upsert','delete','restore']` (§5.2). Зміни схеми й членства — не тут |
| `validateOperation(op, tableSchema)` | Поля §5.2; `upsert` містить **повний** рядок: усі стовпці схеми, невідомі стовпці — помилка (К1) |
| `canonicalOperation(op)` | Детермінований рядок із сортованими ключами; основа для digest, який передається параметром |
| `applyOperation(state, op, { writers, digestOf })` | Результат: `applied`, `duplicate` (той самий `op_id` і канонічні байти), `integrity_violation` (той самий `op_id`, інші байти), `conflict` (розбіжна `base_version`), `rejected` (автор не має права запису на всю таблицю, К6). Стан не змінюється, крім `applied`; конфлікт зберігає обидві версії й останній безконфліктний стан (§5.4) |
| `resolveConflict(state, conflictId, op, { writers })` | Розв'язання — нова операція від учасника з правом запису (К6) |
| `deleteRow` / `restoreRow` (через `applyOperation`) | Надгробок з останнім значенням і автором; відновлення без обмеження за часом (К5); зайнятий ключ при відновленні → `conflict` |
| `diffRows(before, after)` | Змінені клітинки + ознака «надсилається весь рядок» (К1) |

**Тести:** S03, S04, S05; AC03, AC06, AC07, AC08, AC21 (логічна частина; «через довгий час» — зсув
часу параметром); порядок застосування дублів не змінює результату; без LWW (свіжіший `client_time`
не перемагає).
**Межа обсягу:** до 500 рядків коду.

## 2. Порядок і процедура

```text
C1a ──► C1b ──► C1d
  └──► C1c (паралельно з C1b можливий: інші файли)
```

На кожен підетап:
1. Гілка `claude/e8-c1a-sensitivity` (`…-c1b-shared-table`, `…-c1c-membership`, `…-c1d-sync-policy`) від актуального `main`.
2. C2 (розвідка, лише читання), якщо потрібно знайти місця; J3 вибірково перевіряє 2–3 пункти.
3. Тест → реалізація → `verify` з наказу. Лог зберігається в донесенні.
4. PR у `main` (не чернетка), донесення `milestone`.
5. C3 — окремий запуск, лише читання, без міркувань автора: diff, наказ, `AGENTS.md`, ADR, `COLLECTIVES_PLAN.md`; до 15 файлів. Висновок прив'язаний до head-коміту.
6. Виправлення → новий коміт → повторна рецензія C3 на новому коміті.
7. Технічне приймання J3 і змістове J5 на тому самому коміті → злиття. Злиття виконує власник, якщо JE не доручить його J3 (JE-T5).
8. Наступний підетап — від `main` після злиття.

ADM як скрипта немає. За розділом 26 контракту стан і журнал ведуться вручну YAML-файлами:
`tasks/T-0002/` і `reports/T-0002/` в easywar-staff. Роль ADM виконує людина за чек-листом
`done` (розділ 6).
