# T-0014 — End-to-end автономний цикл: наскрізна перевірка «наказ → J4 → J3 → перевірки → C3 → J5 → бар'єр → close» на синтетичній копії

**Статус: ПРОЄКТ НАКАЗУ (чернетка J3 для J5) — не зареєстровано.** Програма JE 2026-10-28 п. 1; підготовка ≠ дозвіл.
**Ініціатор:** J5 · **Виконавець:** J3 · **Координатор:** ADM / J4 · **Режим:** synthetic-only, stub; реальний `j4 close` і `done` у репозиторії — заборонені.
**Залежність:** після T-0012, T-0011, T-0013 (T-0015 — бажано, не обов'язково). Не змінює `bridge/src/**` — лише тести, фікстури, документація, (за дозволом) CI stub.

## 1. Мета

Довести одним відтворюваним прогоном, що автономний цикл **не дає помилкового `done`** і дає правильне `done` лише тоді, коли всі умови
виконані: наказ з `verify`, повідомлення J3, відповіді J5/C3 (stub зі схемою), файл доказів у формі T-0010/T-0012, бар'єр T-0012, ідентичність
установки T-0011, три джерела ескалацій, `close` на **копії сховища** (`J4_STAFF_ROOT`, тимчасова тека). Цикл виконується як тест
(`bridge/test/e2e/*.test.mjs`) і, за окремим дозволом, як `workflow_dispatch` у режимі stub.

## 3. Завдання J3 (після воріт)

1. Фікстури: синтетична задача `T-0900` (наказ з `verify`, `acceptance`, `key_decision: true`), два SHA (A — повний комплект, B — комплект «з дефектом» для кожної умови бар'єра).
2. Тест-сценарій E2E-OK: `task_created` → `task_accepted` → `j4 submit` (J3) → `orchestrate --once` ×N (T-0013) → stub J5/C3 відповідають зі схемою → події ADM з `ref`/`ledger_hash`/`installation_id` → файл доказів → `close` на копії → `done` з `evidence_sha256`; після цього `close` повторно → `already: true`.
3. Тести E2E-NEG (по одному на умову): без `review_status: complete`; `scope: limited`; `scope: full` + `limits`; пізніший збій доказу варіантною `cmd`; `installation_id` не збігається; ескалація відкрита в одному з трьох джерел; стоп-кран; `done` на іншому SHA — кожен має завершитися **без `done`** і з читною причиною в `missing`.
4. Тест відновлення: обрив процесу між `dispatch` і `finalize`, між записом у журнал J4 і `events.jsonl` → `recover()` → цикл завершується без повторного виклику адаптера (лічильник dispatch не зростає).
5. Звіт `reports/T-0014/e2e-report.md`: таблиця сценарій → очікувано → фактично → dispatch; доказ у форматі T-0012 (`{cmd, subject, result}`).
6. За G2(а): job `e2e-stub` (`workflow_dispatch`), артефакт журналу; жоден секрет; `route-live` не чіпати.

**Не входить:** зміни `bridge/src/**` (знайдені дефекти — окремими задачами з `supersedes`-подіями, не правками «по дорозі»), live, планувальник, реальні задачі штабу, автентифікація `by`, EasyWAR.

## 4. Критерії приймання

(1) E2E-OK дає рівно одне `done` на копії й жодного запису в репозиторії; (2) кожен E2E-NEG завершується без `done` із причиною; (3) відновлення не
збільшує dispatch; (4) усі e2e-тести детерміновані (без мережі, без годинника реального часу, крім `at`); (5) лічильник dispatch e2e зафіксований у
`calls-ledger`; (6) C3 за diff тестів і звіту; технічне J3, змістове J5, **остаточне JE**; (7) знайдені дефекти мосту внесені в `risk-register`, не виправлені в T-0014.

## 5. Ліміти й облік (прогноз, не рішення)

Один e2e-цикл у stub ≈ 10–15 dispatch (J3→J5, J5→J3, J3→C3, C3→J3, J5 acceptance) × 9 сценаріїв ≈ 30 (NEG-сценарії зупиняються рано). Повний прогін
після T-0013 ≈ 100. План: повний ×1 (100) + e2e окремо ×1 (30) + CI stub ×1 (130, за G2) → 260; без CI — 130 + резерв 30 → **160**.

## 6. Ризики

R14-1 e2e-тести дорогі за викликами — ними не можна «перевіряти фікстури» (урок T-0012 Р-Т12-10): лише фільтри; R14-2 спокуса виправити
дефект мосту в T-0014 — заборонено scope.out; R14-3 `done` на копії може бути сприйняте як реальне — копія лише в тимчасовій теці, `J4_STAFF_ROOT`, тест перевіряє, що `tasks/T-0900/events.jsonl` у репозиторії не існує.
