# J4 Bridge v0.1 — технічний проєкт

Задача: T-0005 (наказ JE від 21.10.2026). Статус: проєкт і мінімальний прототип; затверджує JE.
Протокол: [PROTOCOL.md](PROTOCOL.md). Поправки до контракту: [tasks/T-0005/amendments.md](../../tasks/T-0005/amendments.md).

## 1. Мета й межі v0.1

J3 (Claude Code) і J5 (GPT) обмінюються структурованими повідомленнями через J4 без ручного
пересилання командиром. J4 — скрипт без власної LLM: перевіряє, маршрутизує, рахує, зупиняє й
записує докази. Рішень по суті J4 не ухвалює.

У v0.1 зроблено: протокол, маршрутизатор, права, ліміти, захист від циклів, ескалація JE, журнал
доказів із ланцюгом хешів, сканер, ворота платних викликів, адаптери (stub, OpenAI Responses API,
Codex CLI, Claude CLI), відновлення після збою, 49 тестів на синтетичних даних, CLI, workflow.

У v0.1 **не** зроблено й не запускалося: живі виклики OpenAI, Codex і Claude (наказ: не запускати
платні API без погодження JE); автоматична постановка задач J5 → C5.1; автоматичні відповіді J3 на
запити J5 (J3 отримує їх у вхідну скриньку); інтеграція з `events.jsonl` задач; GitHub Issues для JE.

## 2. Склад і потоки

```text
                    ┌──────────── easywar-staff (GitHub) ────────────┐
                    │ tasks/T-XXXX/  reports/T-XXXX/  bridge/ledger/  │
                    └───────────────▲──────────────────────▲─────────┘
                                    │ коміт доказів        │ накази, донесення
 J3 Claude Code ──j4 send──►┌───────┴──────────────────────┴───────┐
   (agent_cli)              │ J4 (скрипт, без LLM)                  │
 J3 inbox ◄──deposit────────│  перевірка → маршрут → ліміти → цикли │──sync──► J5: OpenAI Responses API
                            │  → адаптер → відповідь → нове повідом.│◄─reply──  (instructions = roles/J5.md)
 JE ◄──ескалації────────────│  журнал (ланцюг хешів), спул, замок   │──sync──► C5.1-R: codex exec -s read-only
 JE ──resolve (human_cli)──►└───────────────────────────────────────┘──sync──► C5.1: codex exec, власна гілка
```

Звичайний обмін (критерій успіху наказу):

1. J3 у своєму сеансі: `j4 send --from J3 --to J5 ...` — чернетка з `task_id`, `subject` (SHA коміту) і
   хешем контракту.
2. J4 перевіряє форму, контракт, права, маршрут, сканер, нитку й ліміти → `message_accepted`.
3. `j4 run`: J4 резервує бюджет, записує `dispatched` (до виклику), викликає адаптер J5.
4. Відповідь J5 (строгий JSON) → спул → перевірка схеми й сканер → облік → `reply_received`.
5. J4 сам складає повідомлення `J5 → J3` (`kind: response`, `in_reply_to`, `hop + 1`) і пропускає його
   через ті самі перевірки → доставка у вхідну скриньку J3 → `message_delivered`.
6. J3 читає `j4 inbox --role J3`; продовжує нитку або закриває задачу донесенням.

## 4. Маршрутизація

Дозволене лише те, що є в `routes.json`; решта — `route-denied`.

| Від | До | Види |
|---|---|---|
| J3 | J5 | request, response, report, ack |
| J5 | J3 | request, response, ack |
| J5 | C5.1, C5.1-R | request — лише для задачі з `task_accepted` |
| J3 | C5.1-R | request — лише для задачі з `task_accepted` |
| J3 | C3 | request |
| C5.1 | J5 | report, response |
| C5.1 | J3 | handoff (передача коду за розділом 20) |
| C5.1-R | J3, J5 | review |
| C3 | J3 | review |
| будь-хто | JE | escalation |
| JE | будь-хто | command, decision — лише з людського входу |

Доставка: J5, C5.1, C5.1-R — синхронний адаптер (виклик і відповідь); J3, C3 — вхідна скринька
(`J4_HOME/inbox/<роль>/`); JE — ескалації (`J4_HOME/escalations/`).

## 5. Права ролей (пункт 7 наказу)

| Роль | Звідки може писати | Що надсилає | Репозиторій | Злиття |
|---|---|---|---|---|
| JE | лише `human_cli` | command, decision, рішення ескалацій | — | поза мостом |
| J3 | `agent_cli` (свій сеанс), `adapter` | request, response, report, ack, escalation | гілка + PR | ні (JE-T5 поза мостом) |
| J5 | лише `adapter` | response, request, ack, escalation | немає; інструментів немає | ні |
| C5.1 | лише `adapter` | report, response, handoff | власна гілка, `workspace-write` | ні |
| C5.1-R | лише `adapter`, окремий запуск | review | лише читання (`read-only`) | ні |
| C3 | лише `adapter` | review | лише читання | ні |

Ключове правило: **роль відправника відповіді визначає J4 за адаптером**. Агент не може назватися
JE чи іншою роллю — схема відповіді не має поля `from`, а додаткові поля відхиляються.
Незалежність рецензента: інший `run_id`, `sandbox: read-only`, рецензент ≠ автор (`checkIndependence`).

## 6. Ліміти й захист від циклів (пункт 4)

Значення за замовчуванням — `bridge/config/limits.json`; у живому режимі менше з них і погодження JE.

| Ліміт | Значення v0.1 | Що відбувається |
|---|---|---|
| викликів на задачу / на добу | 20 / 50 | `dispatch_blocked`, `auto_on_limit`, ескалація JE |
| токенів на задачу | 60 000 | те саме; резерв 4 000 на виклик |
| вартість на задачу | 0 USD | платний виклик неможливий без погодження з власною межею |
| спроб на виклик | 2 (перша + одна) | третя — лише рішенням JE `third_attempt` (розділ 2) |
| раундів (запитів) у нитці | 4 | `loop-max-rounds`, нитку зупинено, ескалація |
| хопів | 3 | `loop-max-hops` |
| глибина делегування | 1 | `loop-delegation-depth` (розділ 1) |
| відкритих ниток на задачу | 3 | `limit-open-threads` |
| розмір тіла / резюме | 8 000 / 300 | `too-long` |
| вихідних токенів відповіді | 1 500 | `max_output_tokens` у запиті |

Захист від циклів: повтор того самого повідомлення в нитці (`loop-ping-pong`), взаємне очікування
(`loop-wait-cycle`: J5 не може запитувати J3, поки J3 чекає на J5 — зустрічне питання йде як
`response` з `verdict: question`), глибина делегування за ланцюгом `caused_by`, межі хопів і раундів.
Агенти не ініціюють запитів самі: J4 перетворює їхню відповідь лише на `response` адресату-запитувачу.

Стоп-кран: `J4_HALT=1` або файл `bridge/HALT` у репозиторії — J4 не приймає й не відправляє нічого.

## 7. Ескалація рівня C до JE (пункт 5)

Ескалація виникає, коли:
- `decision_level: C` або непорожній `decision_needed` (від J3 чи у відповіді агента);
- вичерпано ліміт, спроби або ворота живого виклику не пропускають;
- спрацював захист від циклу або сканер у відповіді агента.

Що робить J4: повідомлення до адресата не доставляє (стан `held`), нитка переходить у
`awaiting_founder`, запис `escalation_raised` із причиною й категоріями. Питання з `decision_needed`
зберігаються локально, у журналі — лише їхні хеші.

Рішення JE: `j4 resolve --human --id E-... --decision release|reject|resume|halt|third_attempt`.
Приймається лише з людського входу. Наслідки: `release`/`resume` — повідомлення в чергу, нитка
відкрита; `reject` — повідомлення відхилено; `halt` — нитку зупинено; `third_attempt` — одна додаткова
спроба. Пропозиція для робочого режиму — у розділі 10.

## 8. Докази без витоків (пункт 6)

Журнал (`ledger.jsonl`) комітиться в easywar-staff і містить: конверт (задача, нитка, ролі, вид,
рівень, subject, версія контракту), `body_sha256`, авторське резюме (рівень `summary`, можна
вимкнути рівнем `hash`), адаптер і режим, `model_id` і `request_id` **від провайдера**, облік із
`accuracy`, `prompt_sha256`, `raw_sha256`, посилання на погодження JE, рішення маршрутизатора.

Не комітиться ніколи: тексти тіл, інструкції в зібраному вигляді, сирі відповіді, ключі. Сира
відповідь живе в спулі `J4_HOME/spool` (права 0600) лише до запису в журнал і потім видаляється.
Захист у три шари: сканер на вході, сканер відповіді агента, сканер у самому журналі (відмова
записати рядок зі спрацюванням). `j4 verify` перевіряє ланцюг, хеші й відсутність витоків.

Обмеження: сканер — страховка за шаблонами, а не гарантія (розділ 9, п. 4). Основний захист —
synthetic-only і те, що J5 не має доступу до файлів.

## 9. Локальний запуск

```sh
export J4_HOME=$PWD/.j4                      # локальний стан, у .gitignore
export J4_LEDGER=$PWD/bridge/ledger/ledger.jsonl
node bridge/bin/j4.mjs send --from J3 --to J5 --task T-0005 --subject <sha> \
  --intent question --summary "..." --text-file note.md
node bridge/bin/j4.mjs run                  # режим stub; --mode live лише з погодженням JE
node bridge/bin/j4.mjs inbox --role J3
node bridge/bin/j4.mjs escalations
node bridge/bin/j4.mjs resolve --human --id E-T-0005-001 --decision release
node bridge/bin/j4.mjs verify
```

J3 запускає `send` і `run` зі свого сеансу Claude Code, тому командир нічого не пересилає.

## 10. GitHub Actions

Файл `.github/workflows/j4-bridge.yml`:

- `test` — на PR, що змінює `bridge/**`: `node --test`, без секретів, `permissions: contents: read`.
- `route` — `workflow_dispatch` (запускає людина або J3 через `gh workflow run`): режим `stub` або
  `live`. Для `live` job працює в **environment `j4-live`** з обов'язковим рецензентом JE: кожен
  платний запуск JE погоджує кнопкою в GitHub. Секрет `OPENAI_API_KEY` зберігається лише в цьому
  environment. `concurrency: j4-<task>` — один обробник на задачу (до замка J4).
- Журнал із запуску публікується як артефакт; коміт журналу в гілку `j4/ledger` — після рішення JE
  (питання 6), щоб workflow не отримував права запису без потреби.

Налаштування environment (рецензенти, секрети) робить власник репозиторію в GitHub; у PR лише файл.

## 11. Відновлення після збою (пункт 8)

| Збій | Що бачить J4 після перезапуску | Дія |
|---|---|---|
| процес помер до виклику | `queued` | звичайна доставка |
| процес помер під час виклику | `dispatched`, спулу немає | `dispatch_outcome_unknown`; спроба й резерв зараховані (accuracy `estimate`); повтор, якщо є спроби, інакше ескалація |
| процес помер після відповіді | `received` або спул є | фіналізація зі спулу **без повторного виклику** |
| помер між журналом і поданням відповіді | `recorded` із `pending_reply` | подати відповідь один раз (`recovered: submit-reply`) |
| обірваний рядок журналу | неповний останній рядок | відкинути, записати `ledger_repaired` з хешем відкинутого |
| завислий замок | `lock` мертвого процесу або старший за 10 хв | перехопити, `lock_recovered` |
| підробка журналу | невідповідність хешу | `j4 verify` → помилка з номером рядка |

Ідемпотентність: `reply_received` і `reply_blocked` пишуться один раз на `msg_id`; відповідь подається
один раз. З `store: false` OpenAI не дає отримати відповідь повторно, тому невідомий результат
рахується як витрачений виклик — це свідома ціна за відсутність прихованих повторних витрат.

## 12. Загрози

| Загроза | Захист |
|---|---|
| Ін'єкція інструкцій через відповідь J5 | J5 без інструментів і без доступу до репозиторію; відповідь — лише дані в строгій схемі; агент не ініціює запитів; рівень C завжди йде до JE |
| Видавання себе за JE чи іншу роль | роль відправника від адаптера; JE лише з `human_cli`; у CI — лише через environment з рецензентом |
| Неконтрольовані витрати | вартість 0 за замовчуванням; ворота з трьох умов; резерв до виклику; межі викликів/токенів; одна повторна спроба |
| Витік ключа чи даних | ключі лише в змінних середовища; сканер на вході, у відповіді й у журналі; спул локальний і тимчасовий |
| Нескінченний обмін | раунди, хопи, глибина, ping-pong, цикли очікування, стоп-кран |
| Злиття чи зміни production | жодна роль у мості не має права злиття; міст не має команд злиття; C5.1 лише власна гілка |

Відкрите: у локальному запуску «людський вхід» (`--human`) — це довіра до користувача ОС. Справжнє
розмежування дає лише CI з environment. Тому для живого режиму пропоную лише CI (питання 3).

## 13. Обмеження прототипу

- Живі адаптери не викликались: формат `text.format: json_schema` OpenAI і прапорці `codex exec` /
  `claude -p` звірено з довідниками на 21.10.2026, але не підтверджено запуском.
- Вартість рахується лише за ціною з погодження JE (`price`); без неї — `unknown`, межа тримається
  на токенах.
- `model_id` у журналі — значення від провайдера; для `claude -p` і `codex exec` — `null`, доки ADM
  не підтвердить (розділ 7 контракту).
- Перевірки allowlist каталогів (розділ 9, п. 5) для маршрутів J5, C5.1, C5.1-R не проводилися.
- Журнал J4 не пише в `tasks/*/events.jsonl` — це функція ADM; інтеграція запропонована поправкою.

## 15. Питання, що потребують рішення JE

1. **Назва J4 і D-01.** Рішенням D-01 (15.10.2026) J4 перейменовано на ADM («лише скрипт»). Наказ
   T-0005 знову вводить J4 як координатор. Варіанти: (а) J4 — окрема посада-скрипт поруч із ADM;
   (б) міст — функція ADM, позначення J4 лише для мосту. J3 пропонує (б): один скрипт веде облік і
   стан, менше розбіжностей. Поправка A-T5-01.
2. **J5 через API.** J5 у Responses API — інший runtime, ніж ChatGPT, де J5 працював раніше: немає
   пам'яті чату й інструментів, правила ролі — `bridge/roles/J5.md`. Затвердити правила ролі й
