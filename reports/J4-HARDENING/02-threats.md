# 2. Аналіз загроз бар'єра `done` (етап A/B)

Модель: супротивник або помилка намагаються отримати `state_changed: done` без виконаних умов контракту (розд. 6), або
приховати відкриту ескалацію JE. Три класи акторів: (а) помилка сумлінного виконавця; (б) агент із частковим доступом
(відповідь адаптера, файл у `J4_HOME`); (в) особа з правом запису в репозиторій. Клас (в) лежить за межею рівня C (F-9, F-3)
і жодною зміною коду не усувається: вона може вписати `done` напряму. Мета T-0011/T-0012 — закрити (а) і (б) та зробити (в)
видимим у журналі (звірка `ref/ledger_hash`), не змінюючи моделі довіри.

## Нові шляхи обходу, які перевірено на PoC (не з'явились)

- `scope: 'full'` у `review_finished` або `report_filed` на бар'єр не впливає (поле читається лише з `acceptance`).
- `scope` як масив `['A','B']`, число, `null`, відсутнє — усе не `full` → не рахується (SC1-0, SC1-2, SC1-4).
- Запис без `cmd` із `pass` не задовольняє вимогу `verify` (I: `evidence-latest-without-cmd`), тобто «загальний успіх» без команди доказом не є.
- `installation_adopted` для журналу, вже прив'язаного до іншої установки, відхиляється (`ledger-bound-to-other-installation`, I19).
- Правильна пара з хибно закріпленим значенням (помилка в рішенні JE) — відмова, а не тихе проходження (I9).

## Що не входить і чому

Автентифікація `by`/`--human` (F-9/F-3), планувальник, live, зміна ролей — рішення рівня C поза T-0011/T-0012 (G4). Бар'єр під
замком (F-T9-15) — рекомендовано окремим дрібним пунктом після T-0011 (той самий файл `close.mjs`).
