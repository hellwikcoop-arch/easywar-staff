## 4.1. F-T9-16 — формальна повнота записів

**Дефект (підтверджено S16-1/2/4/5):** `evidenceFromEvents` підставляє `review_status: 'complete'`, коли поля немає, а `verdict` є,
і `result: 'accepted'`, коли поля немає. Реальний приклад: `tasks/T-0010/events.jsonl` seq 8 — `review_finished` без
`review_status` (виправлено новою подією seq 10 з `supersedes: 8`; стара не переписана — саме та практика, що й G3).

**Правило після T-0012:** читач не додає жодного поля: `review_status: e.review_status ?? null`, `result: e.result ?? null`,
`scope: e.scope ?? null`. Бар'єр:

| Запис | Нині | Після | Код |
|---|---|---|---|
| `review_finished` + `verdict: passed` без `review_status` | зараховано | **не зараховано** | `review-C3-incomplete` (новий, окремо від `not-passed`, щоб у `missing` було видно причину) |
| … `review_status: null` явно | зараховано | не зараховано | `review-C3-incomplete` |
| … `review_status: partial`/`incomplete` | не зараховано | без змін | `review-C3-incomplete` (нині `not-passed`) |
| … `complete` + `passed` + `ref` | зараховано | без змін | — |
| `acceptance` без `result` | зараховано | **не зараховано** | `acceptance-<by>-<role>-not-accepted` (як для будь-якого не-`accepted`; варіант: окремий `…-result-missing` — не рекомендовано, зайве розгалуження) |
| `acceptance` `result: accepted_with_restrictions` (T-0006 seq 12) | не зараховано | без змін (S16-7) | `…-not-accepted` |

Словник `result` (G2(б)): зараховується лише рядок `accepted`; це вже поведінка коду (`last.result !== 'accepted'`), тож зміна —
лише текст `DESIGN`/`README`/контракту §4 (один рядок): «`result` обов'язковий; інші значення (`accepted_with_restrictions`,
`accepted_scope_AB`, `rejected`) бар'єр не відкривають».

## 4.2. SCOPE-1 — межі приймання

**Дефект (SC1-0…SC1-4):** бар'єр не має поняття «обсяг приймання». Приймання J5 «лише A/B» з `result: accepted` дало б повний
комплект; J5 у T-0009/T-0010 свідомо не створював `acceptance`, а в T-0006 використав `accepted_with_restrictions` (seq 12) і
потім `accepted` (seq 14). Отже, межі нині виражаються або нестандартним `result`, або відсутністю події — обидва способи
тримаються на дисципліні автора.

### Порівняння варіантів структури запису (≥ 2, за наказом)

| | Варіант A — opt-out (`scope: limited`) | **Варіант B — opt-in (`scope: full`)** — рекомендований | Варіант C — компоненти в наказі |
|---|---|---|---|
| Запис `acceptance` | `scope: "limited", limits: ["…"]` позначає часткове; поля немає = повне | `scope: "full"` обов'язковий для зарахування; `scope: "limited"` + `limits: [...]` або відсутність = не зараховується | наказ: `acceptance.components: [A, B, C]`; подія: `accepted_components: [A, B]`; бар'єр вимагає всі |
| Поведінка за замовчуванням | fail-open: забутий `scope` = повне | **fail-closed**: забутий `scope` = не зараховано | fail-closed |
| Старі журнали T-0005…T-0010 | зараховуються як є | не зараховуються (`…-scope-not-full`, compat 4.3) | не зараховуються (немає компонентів) |
| Зміна контракту | §4: один рядок про поле | §4: один рядок про поле; §3 — ні | **§3 (шаблон наказу) і §4** — окреме рішення JE, поза G1 |
| Зміна `orderGate`/`close.mjs` | ні | ні | так (читати `components`) — виходить за `scope.out` |
| Виразність меж | так (`limits`) | так (`limits` — лише документація, бар'єр читає `scope`) | найповніша (бар'єр знає, що саме не прийнято) |
| Нові обходи (перевірено) | забутий `scope` відкриває `done` — це і є дефект SCOPE-1 у новій формі | `scope` у `review_finished`/`report_filed` ігнорується; масив/число/`null`/інший рядок ≠ `full` (SC1-2, 2b, 4) | — (не макетувався) |
| Вплив на тести | 0 | 12 фікстур `acceptance` без `scope` у `t0006`/`t0007`/`t0009` → 16 тестів червоні до оновлення (додати `scope: 'full'`) + нові негативні | більше (наказ, шаблони) |
| Рекомендація | ні (повторює дефект) | **так** | відкласти як розвиток після B (G2 може зафіксувати «B зараз, C — окремим рішенням») |

**Правило варіанта B:** `acceptanceReady` для кожної обов'язкової ролі: останній запис на `subject` → `result === 'accepted'` і
`evidence_ref` → **і** `scope === 'full'`; інакше `acceptance-<by>-<role>-scope-not-full`. **Доповнення за C3 (C3H-2), пропозиція до G2:**
запис `scope: full` із непорожнім `limits` внутрішньо суперечливий → fail-closed: `acceptance-<by>-<role>-scope-contradictory`
(тест SC1-6). Інакше `limits` бар'єр не читає — вони для людей і рецензії. JE вирішує, чи вмикати цю перевірку (рекомендація — так:
вона дешева і прибирає останній спосіб відкрити `done` «за дисципліною автора»). `requiredRoles`/`keyDecision` — без змін: JE для `key_decision` також записує `scope: full`.

**Процедура (для `README`, не код):** J5/J3 пишуть `scope: full` лише коли приймають усі компоненти наказу; часткове —
`scope: limited`, `limits: [...]`, `result: accepted` — тоді зміст прийнято частково, але `done` закритий; повний прийом —
новою подією. Запис із межами лишається в історії й читається рецензентом.

## 4.4. P1 — F-T10-11 / R-11: бар'єр доказів (лише за G4)

**Дефект (R11-1/2/3/6):** `passingCommands` тримає останній запис **за точним рядком `cmd`**, а вимогу `verify` перевіряє
підрядком; збій, записаний варіантною `cmd` (`… --test-reporter`, пробіл наприкінці) або без `cmd`, не скасовує раніший успіх.

**Алгоритм (детермінований, без залежностей):**

```
records := [{cmd|null, pass}] для рядків-записів файла з subject = SHA, у порядку файла, поза блоковими скалярами
якщо records порожній → NOT OK [evidence-no-record-on-subject]
якщо verify порожній:
    для кожної групи за cmd (null — окрема група) останній запис має pass; інакше [evidence-latest-failed:<cmd|<без cmd>>]
інакше для кожної вимоги req ∈ verify:
    related := records, де cmd = null АБО cmd ⊇ req (підрядок, чутливий до регістру, без нормалізації пробілів)
    last := останній у related
    last відсутній            → [evidence-missing:<req>]
    last.cmd = null           → [evidence-latest-without-cmd:<req>]   (запис без команди не доводить вимогу і скасовує попередні)
    last.pass = false         → [evidence-latest-failed:<req>]
pass для запису := resultIsPass(result); result, не розпізнаний як pass («unknown», «see log», порожній…), = збій (fail-closed, C3H-19)
OK ⇔ причин немає; checks[0].passed = OK; evidence_sha256 лише при OK; reasons → missing події відмови
```

Уточнення до PoC (знайдено під час підготовки і рецензією C3, C3H-1; у реалізації обов'язково): **нормалізація `cmd`** — `trim()`;
порожній після цього рядок (`""`, `"   "`) = відсутній `cmd` (нині `''.includes(req)` → false → запис «не стосується» жодної вимоги і
тихо ігнорується — R11-7). **Залишок, задекларований чесно:** запис зі `cmd`, що не є надрядком вимоги (інші лапки
`"bridge/test/*.test.mjs"` замість `'…'`, подвійний пробіл, інший регістр), алгоритм вважає *іншою командою* (контроль R11-5), і
його збій успіху не скасовує. Це межа підрядкового порівняння; канонізація команд (лапки, пробіли) не пропонується, бо вона
сама стала б джерелом помилок розбору; захист — єдина форма `cmd` у донесеннях (README) і рецензія C3 файла доказів.

| Сценарій | Нині | Після |
|---|---|---|
| R11-1 успіх `cmd`, далі збій `cmd --flag` | done | відмова `evidence-latest-failed` |
| R11-2 успіх, далі збій `cmd ` (пробіл) | done | відмова |
| R11-3 успіх, далі збій без `cmd` | done | відмова `evidence-latest-without-cmd` |
| R11-4 збій, далі успіх тієї ж `cmd` (повтор) | done | **done** (контроль) |
| R11-5 збій іншої команди, не з `verify` | done | **done** (контроль) |
| R11-6 успіх варіантною, далі збій базовою | done | відмова |
| R11-7 (новий) успіх, далі збій `cmd: ""` | done (тихо) | **PoC: done** — прогалина PoC; вимога специфікації: відмова `evidence-latest-without-cmd` (трактувати `""` як відсутній `cmd`) |
| R11-8 (новий) `verify` порожній, дві `cmd`, остання запис другої — збій | done («достатньо однієї команди, що пройшла») | відмова `evidence-latest-failed:other` (без `verify` жодна група не може закінчуватись збоєм) |

| Реальні докази `reports/T-0007/001.yaml`, `T-0009/*`, `T-0010/003.yaml` | розбираються | без змін (перевірити тестом, як T-0010 C2) |

## 4.5. R-10 / F-T10-10 і R-12 / F-T10-12 (пропозиція включити в P1)

- **R-10:** заголовок блокового скаляра з тегом/якорем (`note: !!str |`, `- &a >-`, `!custom |2`) не відкриває блок, тому «запис»
  усередині тексту приймається (R10-1/2/3). Правило: перед `|`/`>` допускаються 0…n лексем `!…`/`&…`, розділених пробілами:
  `/(?:^|:|-)[ \t]*(?:(?:![^\s]*|&[^\s]+)[ \t]+)*[|>][+\-0-9]*$/`. Контроль R10-4 (звичайний блок) без змін. Негативні: R10-5 —
  `!!str` **без** індикатора блоку (`note: !!str текст`) блок не відкриває; R10-6 — тег у значенні запису (`{note: !!str x}`) → не доказ
  уже нині (`flowScalar` відкидає `!`).
- **R-12:** (а) тест на порожній рядок усередині блокового скаляра (мутант T-0010 вижив; R12-1 показує, що код правильний, тесту
  немає); (б) `README`: код виходу 1 для `run --once` при нечитній черзі (DESIGN §18 уже є); (в) A5: твердження, що замок знято після
  відмови (C3 підтвердила вручну). Усі три — без зміни поведінки.

## 4.9. Бюджет (оцінка, не рішення): чи вистачає 150 після R-11

Без P1: J3 повний ×1 (48) + CI ×1 (48) = 96, резерв на повтор 48 → 144. З P1 (R-11 + R-10 + R-12 в одному проході): нових
dispatch-тестів немає (усі тести бар'єра — 0 викликів), тож **прогнози однакові — 144/150, запас 6**; один невдалий раунд C3
із повторним повним прогоном вичерпує резерв; другий повтор → HALT. Висновок: 150 **формально достатньо** для одного чистого
проходу з одним повтором і нулем запасу на несподіванки; J3 ліміт не піднімає — питання до J5/JE в G4 (варіанти: лишити 150 з
явним HALT-порогом 144, або 200). Фільтровані прогони (t0006 бар'єр, t0007 S6, t0009 C*, t0010 C*) — 0 викликів, їх можна
повторювати вільно.
