# 3. Специфікація T-0011 — ідентичність установки J4 (етап B)

Статус: **проєкт для рішення JE, не реалізація.** Усі механізми перевірено лише на ізольованій синтетичній копії
`bridge/` (`poc/t0011-poc.patch`, 199 рядків; протокол — `05-experiments.md`, сценарії I1–I19, `evidence/repro-t0011-*.json`).
Жоден захищений файл не змінювався. Специфікація не змінює модель довіри (G4): вона захищає від **помилкового** вибору пари
`J4_HOME`/`J4_LEDGER` і від **спрощеної** підміни, робить навмисну підміну видимою в журналі задачі, але особу автора
(`by`, `--human`) не доводить (F-9, F-3).

Терміни: **marker** — файл `J4_HOME/installation.json`; **прив'язка журналу** — запис журналу J4, що називає установку;
**закріплене значення** (pinned) — значення, яке JE фіксує поза кодом і яке CLI отримує явно; **пара** — `J4_HOME` + `J4_LEDGER`.

## 3.1. Мета й межі

`j4 close` і `run --once` відмовляють, якщо marker сховища, прив'язка журналу, закріплене значення й події J4 у
`tasks/<id>/events.jsonl` не належать одній установці (усуває F-T9-18, S18-2/S18-6). Правильна пара → поведінка без змін
(I1, I2, I15, I17). Межі — за наказом: `store.mjs`, `ledger.mjs` (у наказі не названий — потрібне уточнення, див. 3.9),
`close.mjs`, `router.mjs`, `bin/j4.mjs`, новий `test/t0011.test.mjs`, `DESIGN`, `README`. Не входить: `acceptance.mjs`,
автентифікація, планувальник, live, реальний `j4 close`, реальна установка (G6).

## 3.2. Два дизайни прив'язки журналу (порівняння)

| Критерій | Дизайн 1 — запис у журналі (PoC) | Дизайн 2 — хеш у marker-і |
|---|---|---|
| Де лежить прив'язка | seq 1 `installation {installation_id}`; для старих журналів — `installation_adopted {installation_id, first_hash, adopted_at_seq}` | `installation.json` містить `installation_id` і `ledger_first_hash` (хеш seq 1 наявного журналу) |
| Захищено ланцюгом хешів | так: підмінити прив'язку = переписати весь журнал | ні: marker — звичайний JSON, що змінюється файлом |
| Зміна `ledger.mjs` | так (конструктор з `installationId`, `adopt`, `ledgerInstallation`) | ні |
| Зсув `seq` у новій установці | так, на 1 (перший запис — `installation`) | ні |
| Вплив на наявні тести | 4 твердження за номером запису (`recovery` «підробка запису», `t0009 E1 seq 3`, `t0010 D1 length 3`, `t0007 S7 lines[0]`) + усі `closeTask`/CLI-тести `close` потребують закріпленого значення (t0009 C1–C8: 14 бібліотечних + 7 CLI; t0010 A3, B2, D1, D2, E1) | лише тести `close` (те саме закріплене значення) |
| Коли журнал порожній до першого повідомлення | прив'язка з'являється при створенні `J4` (конструктор роутера) — до першого повідомлення | `ledger_first_hash` можна записати лише після першого запису → marker мутабельний або неповний у вікні |
| Міграція старої установки | `adopt --human` дописує `installation_adopted` в голову — історія не переписується (I18) | дописати `ledger_first_hash` у marker — також без переписування |
| Виявлення підміни журналу тієї ж установки | однаково: за `ref/ledger_hash` подій ADM (I13) | однаково |
| Рекомендація | **рекомендований**: прив'язка в незмінному ланцюзі, один механізм для нового й старого журналу | запасний, якщо JE відкине зміну `ledger.mjs` (3.9) |

Вибір дизайну — пропозиція до G1 (3.8). Далі специфікація описує Дизайн 1 і позначає, де Дизайн 2 відрізняється.

## 3.3. Механізми (10) з позитивними і негативними сценаріями

Позначення сценаріїв: I-номери — відтворені на PoC (`evidence/repro-t0011-poc.json`); N-номери — нові, для `t0011.test.mjs`
(`07-draft-tests/t0011.draft.test.mjs`). Коди відмови — поле `code`, деталі — `missing[]`; код виходу CLI — 3 (як у всіх
відмов `close`), стоп-кран 4 — без змін.

### M1. Ідентифікатор установки (marker)

- `Store` з `create: true` один раз пише `installation.json`: `{installation_id: <32 hex, randomBytes(16)>, created_at: ISO, format: "j4.installation/1"}`, атомарно (`writeJson`: tmp + rename), права 0o600 (як інші файли сховища). Наявний marker ніколи не переписується.
- `Store.open` (лише читання, T-0010) marker **не створює**: `close` на чужій теці слідів не лишає (I6 → `store-marker-missing`).
- `store.installation()` повертає marker або `null`, якщо файла немає, він не об'єкт, `installation_id` не 32 hex, або `format` невідомий.
- Ідентифікатор локальний, нікуди не передається, не є `installation_id` лічильника встановлень EasyWAR (`AGENTS.md`, Q13) — у `DESIGN`/`README` це сказати явно.
- Позитивні: I1/I2 (правильна пара); N1 — повторний `new Store(home)` не змінює `installation_id`. Негативні: I6 (marker відсутній), N2 — marker не JSON / масив / `installation_id` 31 символ / `format: "j4.installation/2"` → `store-marker-missing` (не виняток); N3 — `installation.json` є текою → `store-marker-missing`.

### M2. Прив'язка журналу до установки

- Дизайн 1: конструктор `Ledger(file, {installationId})` до **порожнього** журналу (розмір 0) дописує seq 1 `{event: "installation", at, detail: {installation_id}}`; непорожній журнал не змінюється (прив'язка — лише через M10). `ledgerInstallation(entries)`: seq 1 `installation` з 32-hex id → id; інакше перший `installation_adopted`, чий `first_hash === entries[0].hash` → id; інакше `null`.
- Роутер передає `installationId: store.installation()?.installation_id ?? null`: нова установка прив'язується до першого повідомлення.
- Позитивні: I2; N4 — новий роутер на новому сховищі: `entries[0].event === 'installation'`, `seq === 1`, ланцюг валідний. Негативні: I7 (чужий журнал → `ledger-binding-mismatch`), I10 (журнал обрізано до seq 1 → прив'язка ціла, але ескалація зі сховища лишається видимою → `open-escalation`), N5 — журнал із seq 1 іншої події (стара установка) → `ledger-not-bound`.

### M3. Перший хеш (`ledger_first_hash`) і мінімальний seq

- Закріплювані JE значення (G3): `installation_id` (обов'язково), `ledger_first_hash` (рекомендовано), `ledger_head_seq` на момент рішення (необов'язково). Відкриті прапорці CLI: `--installation <id>` / `J4_INSTALLATION_ID`, `--ledger-first-hash <sha256>` / `J4_LEDGER_FIRST_HASH`, `--ledger-min-seq <N>` / `J4_LEDGER_MIN_SEQ`.
- Перевірка: `entries[0].hash === first_hash` (якщо задано) → інакше `installation-mismatch[ledger-first-hash-mismatch]`; `entries.length >= min_seq` (якщо задано) → інакше `installation-mismatch[ledger-truncated-below-min-seq]`.
- Навіщо: ланцюг хешів не виявляє обрізання до префікса (префікс — валідний ланцюг); `ledger_min_seq` закриває T8/I11 для записів до закріпленого seq, події ADM (M7) — для синхронізованих.
- Позитивні: N6 — правильний `first_hash`, `min_seq` ≤ довжини → без змін. Негативні: N7 — `first_hash` іншого журналу → відмова; N8 — журнал тієї ж установки обрізано нижче `min_seq` → відмова (закриває I11 у межах закріпленого seq); N9 — `min_seq` не ціле / від'ємне → `installation-unknown[ledger-min-seq]` (fail-closed на вході, не тихе ігнорування).
- Дизайн 2: `first_hash` живе в marker-і замість закріплення — тоді перевірка marker ↔ журнал обов'язкова, закріплення JE лишається для `installation_id`.

### M4. Закріплене значення обов'язкове (fail-closed)

- Без `--installation`/`J4_INSTALLATION_ID` або з хибним форматом → `installation-unknown[pinned]` **до** будь-якої іншої перевірки (I3, I4). Значення з `bridge/config/**` не читається (захищена тека, G3): код не має «значення за замовчуванням».
- Хибне закріплене значення для правильної пари (помилка в рішенні JE) → `installation-mismatch[store-marker-mismatch, ledger-binding-mismatch]` (I9), а не тихе проходження.
- Негативні: N10 — `--installation` з великими літерами hex → відмова (формат строго `^[0-9a-f]{32}$`; CLI не нормалізує — або нормалізувати явно й це задокументувати; пропозиція: не нормалізувати).

### M5. Виявлення підміни й обрізання журналу

- Уже є: `readLedgerStrict` (відсутній, обірваний, порушений ланцюг, зміна під час читання). Додається: (а) звірка подій ADM (M7); (б) `ledger_first_hash`/`ledger_min_seq` (M3); (в) прив'язка seq 1 (M2).
- Матриця: підміна одного запису → `ledger-corrupt` (ланцюг) — є; підміна з перерахунком усього ланцюга тієї ж установки → `event-seq-N:ledger-seq-M-mismatch` (I13), якщо є синхронізована подія, інакше `ledger-truncated-below-min-seq`/`ledger-first-hash-mismatch` (M3); інша установка → M2/M6; обрізання до префікса → M3 (`min_seq`) або M7.
- Залишок, який чесно задекларувати в `DESIGN`: журнал тієї ж установки обрізано до seq ≥ `min_seq`, подія ескалації ще не синхронізована, сховище — чистий знімок (I11). Закривається процедурно: `run --once --task-events` регулярно (рекомендація — у `j4-tick.sh` він уже є) і оновлення `ledger_min_seq` у кожному рішенні JE про `close`.

### M6. Відмова на чужому сховищі

- `checkInstallation` збирає всі розбіжності, а не першу: `store-marker-missing` | `store-marker-mismatch`, `ledger-not-bound` | `ledger-binding-mismatch` (I5–I9). Код — `installation-mismatch`.
- Порядок у `closeTask`: після читання `events.jsonl` (щоб `events-corrupt` лишився першим), **перед** `already` (I16: повтор після `done` на чужій парі — відмова, а не `already`), перед `orderGate`.
- У CLI `close` порядок лишається: `halted` → джерела задані → `inspectJ4Home` → `readLedgerStrict` → `closeTask` (усередині — M4/M6). У `run --once`: роутер при створенні порівнює `store.installation()` і `ledgerInstallation(entries)`; якщо обидва є й різні → виняток `installation-mismatch`, код виходу 1 (як для нечитної черги, T-0010 A5), запису в журнал немає. Сховище без marker-а + журнал прив'язаний (або навпаки) у `run` — лише попередження в stderr і подія `installation_unbound` у журналі? **Пропозиція: ні — також відмова**, інакше J4 продовжить писати в журнал іншої установки; виняток для міграції — `adopt` (M10). Це питання до G1.
- Негативні: I5–I9, I16, N11 — `run --once` із чужим прив'язаним журналом → код 1, журнал не змінено (довжина й голова ті самі).

### M7. Звірка ескалацій і подій J4 за трьома джерелами

Нині `openEscalations` об'єднує «відкриті» зі сховища, журналу J4 і `events.jsonl`. Додається звірка **ідентичності** джерел:

1. Кожна подія ADM у `events.jsonl` з `ref: j4-ledger#seq=N` і `ledger_hash` → запис N наданого журналу існує і `hash` збігається; інакше `ledger-events-mismatch[event-seq-S:ledger-seq-N-mismatch]` (I12, I13). Подія ADM без `ref` на журнал (`done`) не звіряється.
2. Якщо подія має `installation_id` (лише за G2) — має дорівнювати закріпленому (I14: `event-seq-S:installation-mismatch`). Без G2 поле не пишеться і не перевіряється; I14 тоді покривається лише п. 1 (хеш чужого журналу не збіжиться — але лише якщо seq N існує в наданому журналі; якщо ні — `mismatch` також).
3. Для події `escalation` з `ref seq=N`: запис N має бути `escalation_raised` з тим самим `escalation_id` (інакше `event-seq-S:ledger-seq-N-kind-mismatch`) — нове порівняно з PoC, щоб підміна виду запису не проходила при однаковому хеші (теоретично неможлива без зміни хешу, але перевірка дешева і робить мутант помітним).
4. Ескалація `open` у сховищі, невідома журналу (немає `escalation_raised`) → `installation-mismatch[store-ledger-escalation-unknown]` (перенесення правила `store-ledger-mismatch` з `tasks/T-0009/tools/reconcile-close.mjs`): сховище і журнал одної установки не можуть розходитись у наборі ескалацій, бо `escalate()` пише обидва під замком. Виняток — збій між двома записами: тоді правильна дія — `recover`/повторний такт, не `close`.
5. Чужий `events.jsonl` (із `task_id` іншої задачі) не читається — `readTaskEvents` уже фільтрує; подія з `ref` на seq, якого в журналі ще немає (N > довжини) → `mismatch` (журнал коротший за посилання — обрізання).

Позитивні: I12→після `resolve` = I15 (`done`), N12 — три джерела узгоджені, 2 ескалації, обидві вирішені → `done`. Негативні: I12, I13, I14, N13 (п. 3), N14 (п. 4), N15 (п. 5: `ref seq=99` при 5 записах).

### M8. Поведінка при перезапуску і збої

- `close` до єдиного запису `done` нічого не пише: усі нові перевірки — читання; повтор після будь-якої відмови безпечний.
- Збій між записом marker-а і seq 1 журналу (новий роутер): marker є, журнал порожній → наступний запуск роутера допише seq 1 (журнал усе ще розміру 0) — самовідновлення; якщо встигло записатись інше повідомлення без seq 1 (неможливо за кодом: конструктор пише seq 1 синхронно до будь-якого `append`), це `ledger-not-bound` → `adopt`.
- Обірваний останній рядок: `readLedgerStrict` → `ledger-partial` (без змін); `adopt` на такому журналі має відмовити (`ledger-partial`), а не дописувати після обірваного рядка (PoC цього не перевіряє — N16 обов'язковий).
- Замок: `close` замка сховища не бере (лише читання); `adopt` — під замком журналу (`append`), сховище — `writeJson` атомарний.
- Негативні: N16 (adopt на обірваному журналі → відмова, файл не змінено), N17 (marker написано, журнал порожній → після створення роутера seq 1 є і один).

### M9. Режим без журналу

- CLI: `J4_LEDGER` обов'язковий (T-0009 C3/C6) — без змін. Бібліотека: `ledgerEntries: []` допускається лише свідомо (T-0009 C5); після T-0011 порожній список означає `ledger-not-bound` → `installation-mismatch`. Тест C5 (`clone … ledgerEntries: []` → `ok: true`) зміниться на очікування відмови; це **задумана** зміна поведінки (у тесті вже зафіксовано, що такий виклик небезпечний).
- Журнал новоствореної установки ніколи не порожній (seq 1), тому «порожній журнал» після T-0011 = або стара установка до `adopt`, або чужий файл → відмова в обох випадках.
- Сценарії: N18 (`ledgerEntries: []` → `installation-mismatch[ledger-not-bound]`), N19 (CLI з `J4_LEDGER` на порожній файл → `ledger-missing`? ні: файл є, 0 записів → `readLedgerStrict ok, entries []` → `installation-mismatch[ledger-not-bound]`).

### M10. Міграція без втрати історії

- Команда `j4 adopt --human [--home … --ledger …]`: (1) `new Store(home)` — створює marker, якщо його немає (єдине місце, де `close`-контур пише в сховище; виконується лише людиною за рішенням JE); (2) порожній журнал → seq 1 `installation`; непорожній без прив'язки → `installation_adopted {installation_id, first_hash: entries[0].hash, adopted_at_seq: entries.length}` у голову; (3) прив'язаний до того ж id → `already`; до іншого → `ledger-bound-to-other-installation`, код 3 (I18, I19).
- `ledgerInstallation` приймає `installation_adopted` лише з `first_hash`, що дорівнює фактичному хешу seq 1: перенесення запису в інший журнал не спрацює.
- Виведення `adopt` (installation_id, seq, first_hash) — це саме ті значення, що JE закріплює (G6): команда друкує їх і більше нічого не змінює.
- Негативні: N16, N20 — `adopt` без `--human` → помилка використання, нічого не записано; N21 — два `adopt` поспіль → другий `already`, журнал не зріс.
- Після приймання: `tasks/T-0009/runbook-close.md` скоротити до посилання на `DESIGN`, `reconcile-close.mjs` або перенести правила в `close.mjs` (M7 п. 4 це робить) і прибрати, або лишити з поясненням «дубль для ручної звірки» — рішення в плані (`09-plan-T-0011.md`).

### M11 (додатково). Захист від хибного `done`

Підсумок порядку перевірок у `closeTask` після T-0011 (**єдиний нормативний порядок**, C3H-3): `subject` → джерела передані →
`events.jsonl` читний → **ідентичність пари (M4, M6, M3)** → `already`/`done-exists-other-subject` → наказ → **звірка подій і
ескалацій (M7)** → бар'єр (`acceptance.mjs`, без змін) → запис. Отже повторний `close` уже закритої задачі на правильній парі дає
`already`, навіть якщо в журналі задачі є застаріла подія ADM (тест N23). **PoC від цього відхиляється** (звірка подій усередині
`checkInstallation` до `already` — PG-6) і в реалізації приводиться до M11. Факт для міграції: у реальних `tasks/T-0005…T-0010/events.jsonl`
подій ADM із `ref: j4-ledger#seq=N` немає (0 з 124 подій; `--task-events` не вмикали), тож M7 на них нічого не звіряє і хибних
відмов не створює. Жодна нова перевірка не послаблює наявну; усі нові — лише додаткові причини відмови.

## 3.4. Формати даних

```jsonc
// J4_HOME/installation.json
{"installation_id":"<32 hex>","created_at":"2026-…Z","format":"j4.installation/1"}
// журнал J4, seq 1 (нова установка)
{"event":"installation","at":"…","detail":{"installation_id":"<32 hex>"},"seq":1,"prev":"000…0","hash":"…"}
// журнал J4, міграція (будь-який seq)
{"event":"installation_adopted","at":"…","detail":{"installation_id":"<32 hex>","first_hash":"<sha256 seq 1>","adopted_at_seq":N},"seq":N+1,"prev":"…","hash":"…"}
// подія ADM у events.jsonl — лише якщо G2 затверджено
{"seq":…,"event":"escalation","by":"ADM","ref":"j4-ledger#seq=N","ledger_file":"ledger.jsonl","ledger_hash":"…","installation_id":"<32 hex>", …}
```

Сканер (`scanObject`) має пропускати 32-hex і sha256 — вже пропускає (хеші в журналі є). Жодне з полів не є секретом і не є даними EasyWAR.

## 3.5. Коди відмови (нові) і де вони з'являються

| Код | `missing[]` | Де |
|---|---|---|
| `installation-unknown` | `pinned`, `ledger-min-seq`, `ledger-first-hash` | закріплене значення відсутнє/хибного формату |
| `installation-mismatch` | `store-marker-missing`, `store-marker-mismatch`, `ledger-not-bound`, `ledger-binding-mismatch`, `ledger-first-hash-mismatch`, `ledger-truncated-below-min-seq`, `store-ledger-escalation-unknown` | пара не належить закріпленій установці |
| `ledger-events-mismatch` | `event-seq-S:ledger-seq-N-mismatch`, `event-seq-S:ledger-seq-N-kind-mismatch`, `event-seq-S:installation-mismatch` | `events.jsonl` посилається не на цей журнал |
| `ledger-bound-to-other-installation` | — | лише `adopt` |

Код виходу CLI: 3 для всіх (узгоджено з наявними відмовами `close`); `run --once` при розбіжності — 1.

## 3.8а. Що T-0011 НЕ доводить (уточнення за C3H-4)

Закріплене значення публічне (рішення JE в репозиторії), ланцюг хешів журналу без ключа, seq 1 детермінований. Актор із правом
запису в `J4_HOME`/`J4_LEDGER` і читанням оригінального журналу може зібрати «чисту» пару: marker = закріплене, seq 1 скопійовано
(`first_hash` збігається), ланцюг перераховано, довжина ≥ `min_seq`. M3/M4/M6 це пропускають; ловить лише M7 — і лише коли хоч одна
подія J4 вже синхронізована в `events.jsonl`. Тому для актора (б)/(в) залишок T7/T9 той самий, що T8: вікно до синхронізації.
T-0011 захищає від помилки й спрощеної підміни і робить навмисну видимою, якщо `--task-events` увімкнено регулярно (рекомендація:
кожен такт). Ротація/архівація `ledger.jsonl` **не підтримується**: один файл на установку; після ротації seq 1 ≠ `installation` →
`ledger-not-bound`, і потрібен новий `adopt` + оновлені закріплені значення (C3H-9; задекларувати в DESIGN).
