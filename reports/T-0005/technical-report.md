## Підсумок

Перший етап виконано: проєкт, протокол і мінімальний прототип. Критерій успіху виконано **в режимі
stub**: J3 надіслав повідомлення через J4, J4 автоматично отримав відповідь і доставив її J3, обидва
повідомлення зафіксовано в журналі з ланцюгом хешів. Відповідь дав синтетичний адаптер без LLM, а не
J5, бо живий виклик OpenAI заборонений до погодження JE. Повна перевірка з J5 — один погоджений
виклик (питання 4).

## Архітектурні альтернативи

Порівняння шести варіантів — `bridge/docs/DESIGN.md`, розділ 14. Коротко: рекомендую скрипт-маршрутизатор
(A, цей прототип) із журналом у git (B як транспорт доказів). Codex як MCP-сервер (C) — доповнення для
J3 ↔ C5.1 пізніше. Транспорт через коментарі GitHub (D), оркестратор Agents SDK (E) і автоматизацію
чату ChatGPT (F) не рекомендую: публікують промпти, додають LLM у J4 або крихкі.

## Обмеження

- Відповідь у демонстрації — stub, не J5.
- Формат структурованого виходу Responses API і прапорці `codex exec` / `claude -p` звірено з
  довідниками, але не підтверджено запуском.
- Вартість без ціни з погодження JE — `unknown`; межу тримають токени.
- «Людський вхід» у локальному CLI — довіра до користувача ОС; надійне розмежування — environment у CI.
- Журнал J4 не пише в `events.jsonl` задач (поправка A-T5-04).
