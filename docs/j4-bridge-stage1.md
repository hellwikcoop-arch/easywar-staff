# J4 Bridge v0.1 — Етап 1

**Статус:** синтетичний прототип для перевірки JE та J5. Автономний режим і живі адаптери не увімкнено.

## Підстава та межа

Прочитано `CONTRACT_v0_4.md` із гілки `setup/staff-bootstrap`, розділи 0–9, 12–13, 23–26, а також README і `docs/migration.md`. SHA-256 контракту: `f09ed2a2bca43e80bbdbb604c3d71ca8208f06b676f4b18681c14f96b06a1e8e`. Він є чернеткою, хоча рішення JE-T4 застосувало його як робочий контракт до T-0002. Рішення D-01 перейменувало J4 на **ADM**. Назва «J4 Bridge» у цьому етапі — назва компонента з наказу, а не нова посада чи зміна контракту. Потребує рішення JE перед живим запуском.

`main` репозиторію зараз містить лише README. Ця гілка відгалужена від `setup/staff-bootstrap` (відкритий PR #1); PR Етапу 1 слід рецензувати відносно цієї бази.

## Архітектура

```text
J5 (Codex CLI) ⇄ [валідація → ліміти → маршрутизатор → журнал] ⇄ J3 (Claude API)
                              │
                              └→ черга рішень рівня C → JE

GitHub: майбутній журнал задач, рішень і доказів; у Етапі 1 є локальний JSONL.
```

Координатор детермінований і не має власної LLM. `j4_bridge/core.py` містить перевірку конверта, маршрути J3↔J5, чергу JE, облік бюджету Claude, ліміти та бар'єр приймання. `MockAdapter` є **єдиним** дозволеним адаптером цього етапу. Обидва напрямки перевіряються без мережі. Журнал JSONL лише додається; повторний запуск відтворює ID, раунди, спроби, виклики й витрати поточного місяця. Це окремий демонстраційний журнал, не офіційний `events.jsonl` ADM. Прототип розрахований на один процес і не захищає від одночасних записів або збою між доставкою та записом; живий адаптер не підключати до усунення цих меж.

### Конверт повідомлення

Обов'язкові поля: `message_id`, `task_id`, `sender`, `recipient`, `commit_sha` (повний SHA-1), `kind` (`task|question|decision|report`), `status`, `at` (ISO 8601 з часовим поясом), `body`, `data_class: synthetic`, `round`, `step`, `attempt`. Для `decision` потрібен `decision_level`. Рівень `C` йде лише до JE зі станом `awaiting_je`, без автоматичного затвердження. Горизонтальний запит J5↔J3 у живій версії стає завданням тільки після `task_accepted` згідно з контрактом; цей прототип не видає дієвих наказів.

Маршрутизатор відхиляє повторний ID, повторний зміст, пропущений або перевищений раунд, третю спробу та перевищення викликів. Початкові ліміти прототипу: 8 раундів на задачу, 2 спроби на крок, 40 доставок на задачу. Це **параметри прототипу**, не поправка до наказу. Майбутній адаптер мусить брати `max_calls` та інші ліміти з чинного наказу. Третя спроба в прототипі завжди заблокована; контракт дозволяє її лише для важливої події після рішення JE.

### Бюджет Claude API

Одиниця — цілі центи USD; місяць визначається за UTC. До доставки на J3 перевіряється верхня межа витрат виклику. Від $35 формується `warning_35_usd`, від $45 — `critical_45_usd`, на $50 — `stop_50_usd`; за досягнення $50 нові модельні доставки J4 до J3 і J5 зупиняються, а рішення рівня C ще можна поставити в чергу JE. Якщо верхня межа може перевищити $50, виклик відхиляється заздалегідь. Витрати відтворюються з журналу після перезапуску. Це ліміт **викликів J4**, а не гарантований рахунок організації. Перед живим запуском потрібні підтверджене джерело фактичної вартості, початковий баланс місяця, верхня межа ціни запиту і взаємне блокування кількох процесів. Без них живий адаптер має залишатися вимкненим.

Anthropic [Messages API](https://platform.claude.com/docs/en/api/messages/create) повертає `usage` у токенах. Організаційний [Usage and Cost API](https://platform.claude.com/docs/en/manage-claude/usage-cost-api) потребує окремих адміністративних прав; його дані зазвичай з'являються приблизно за 5 хвилин, іноді пізніше. Тому післяфактум звіт сам по собі не гарантує жорсткої межі $50. У live-дизайні резерв має спиратися на перевірені тарифи та максимальні токени, а звіт витрат — узгоджувати журнал; якщо резерв або вартість невідомі, виклик не починати.

### Приймання й GitHub

`acceptance_ready` вимагає для **того самого SHA**: доказу успішних перевірок, повної рецензії C3 з `passed`, нуля відкритих обов'язкових зауважень, окремого технічного приймання J3 та змістового приймання J5. Для `key_decision` додається приймання JE. Функція лише перевіряє надані записи; вона не посвідчує справжність ролі чи файлів і не змінює стан на `done`. У живій інтеграції потрібна перевірка авторства та доказів через GitHub і чинний наказ. Автоматичного злиття PR немає.

Майбутній GitHub-адаптер має додавати посилання на задачу/PR/коміт і доказ у журнал, перевіряти незмінність `subject` та не редагувати чужі донесення. Події контракту `task_created`, `task_accepted`, `report_filed`, `review_finished`, `acceptance` та `command` мають лишатися окремими від транспортних повідомлень. Підпис JE та схвалення рівня C не виводяться із тексту відповіді моделі.

## Перевірка прототипу

```sh
python3 -m unittest discover -s tests -p 'test_j4_bridge.py' -v
python3 -m j4_bridge
```

Усі фікстури синтетичні. CI виконує тільки ці локальні тести. Платні API-виклики, ключі, секрети, реальні дані й основний застосунок EasyWAR не використовуються.

## Підключення після окремого рішення

1. **Claude.** Власник обирає організацію, workspace, модель, тариф і спосіб обліку. [Офіційний Python SDK](https://platform.claude.com/docs/en/api/sdks/python) підтримує Messages API. Локально `claude` CLI не знайдено; доступність Claude API для цього облікового запису не перевірялась платним запитом. Облікові дані передаються лише через захищений локальний механізм середовища/сховища секретів; ключі не запитуються в чаті й не потрапляють у репозиторій або журнал. Перед реалізацією адаптера перевірити фактичні `model_id`, інструменти, ліміти, максимальну вартість і права до [звітів витрат](https://platform.claude.com/docs/en/manage-claude/usage-cost-api). Окремо провести тест allowlist каталогів, включно з обходом через symlink.
2. **Codex на MacBook.** Перевірено локально: `codex-cli 0.163.0-alpha.11`, `codex login status` → `Logged in using ChatGPT`, `codex exec --help` доступний. Це перевірка встановлення та способу входу, **не** пробний inference-виклик. Майбутній адаптер викликає `codex exec` у виділеній синтетичній робочій копії, з обмеженням каталогів, без секретів у prompt чи аргументах; структурований результат і фактичний доступ до моделі перевіряються окремим інтеграційним тестом.
3. **CI.** ChatGPT-вхід на цьому MacBook не переноситься автоматично на GitHub Actions. Офіційний [`openai/codex-action`](https://github.com/openai/codex-action) зараз вимагає API-ключ провайдера; [OpenAI workload identity federation](https://developers.openai.com/api/docs/guides/workload-identity-federation/github-actions) є окремим варіантом для OpenAI API. Вибір схеми CI, витрат і прав потребує рішення власника. У цій гілці CI запускає тільки безкоштовні тести.

## Відкриті рішення та умови наступного етапу

- JE: узгодити назву `J4 Bridge` з чинною роллю ADM та визначити, чи це той самий компонент.
- JE/J5: визначити джерело стартового місячного балансу, workspace, тариф і правила зупинки, коли звіт Anthropic затримується або ціна невідома.
- J5/J3: затвердити схему GitHub-журналу, авторизацію ролей, `task_accepted`, підписи JE та синхронізацію без дублювання подій.
- Провести окремий інтеграційний тест Claude API і Codex CLI на синтетичних даних після дозволу на витрати; перевірити allowlist, restart/concurrency, відмови провайдерів і приймання на реальному PR.
- Провести незалежну рецензію C3, технічне приймання J3 та змістове приймання J5 на одному коміті; рішення JE потрібне для питань рівня C. До цього `done` і автономна робота не заявляються.
